# SwingBridge Emulators

Runtime emulation of the Swing API on top of Vaadin 25. Goal: take an existing Swing desktop application, swap `javax.swing` imports for `vaadinx.swing`, recompile, and run it as a Vaadin 25 web app — as a migration bridge to a future native-Vaadin rewrite, not a permanent target.

The runtime-emulation approach is validated and no fundamental blocker has surfaced. The objective is **full Swing coverage** — all supported Swing components, all major scenarios — with Sampler as the load-bearing testbed. Work proceeds component-by-component, surrogate-first per [D_surrogate_first](./emulators/decisions.md#D_surrogate_first), slow-and-methodical; each slice ships with a Sampler demo and a `WarnInventoryTest` exit gate.

**Vaadin Push is mandatory.** The emulator runtime depends on it: `EHelper.callSwing` (R_callswing_envelope) runs every Swing listener as a UI fiber of [vaadin-blocking-dialogs](https://github.com/mvysny/vaadin-blocking-dialogs), which parks a modal Swing dialog's caller on a virtual thread, and the resulting server-side UI mutations only reach the browser when `@Push` is enabled on the host `AppShell` ([D_callswing_loom](./emulators/decisions.md#D_callswing_loom)). Without Push a blocking `dialog.show()` / `JOptionPane.show*` never renders. Emulator code may assume Push is on and never needs to guard for its absence — a missing-Push deployment is a host-app misconfiguration, not a case the library degrades around.

**JDK 24+ is mandatory (build and runtime), and JDK 21 will not be supported while `callSwing` runs on virtual threads** (closed as won't-implement, 2026-09-07). `EHelper.callSwing` parks its virtual thread on a carrier that is **the Vaadin request thread holding the session lock** (a UI fiber's continuations run as the session's access tasks, in vaadin-blocking-dialogs' loom runner). Pre-[JEP 491](https://openjdk.org/jeps/491), a virtual thread that parks inside a `synchronized` region pins its carrier — so on JDK 21 the request thread blocks with the lock held, the response never flushes, the dialog never renders, and the click that would unpark the thread can never arrive. That is a deterministic deadlock independent of core count, not pool starvation. Measured: `JOptionPane.showConfirmDialog` inside a plain `synchronized` block hangs every time on Temurin 21.0.11 and completes on JDK 25 (2026-09-07); the `SwingWorker` → `java.util.prefs` bridge, which parks inside `AbstractPreferences`' JDK-owned monitor, failed the same way in CI (2026-07-21). **The trigger is any monitor above a modal call** — the migrator's `synchronized void save()`, `Object.wait`, third-party and JDK-owned locks — so it lives in code SB-Emulators never sees and cannot be swept or worked around; only JEP 491 (JDK 24) removes it. Bytecode still targets Java 21 (migrator compile compat); the enforcer plugin gates the *build* at `[24,)`; CI runs on JDK 24 and 25; and `SwingBridgeEmulatorsBootstrap` refuses an older *runtime* at servlet init (R_match_swing_errors case (6)), since a build on 24 deployed onto 21 passes every build gate. The floor belongs to the loom strategy, not the project: a blocking strategy that parks a platform thread instead (vaadin-blocking-dialogs' planned [session-unlock runner](https://github.com/mvysny/vaadin-blocking-dialogs/blob/master/design/ideas/session-unlock-runner.md)) carries no JDK floor of its own.

## Terminology

**The project's name is "SwingBridge Emulators", "SB-Emulators" for short** ([D_naming_scheme](./emulators/decisions.md#D_naming_scheme)). Full name on first use per document, then SB-Emulators wherever the *whole project* is meant; module notation (`:emulators`, `:surrogates`) wherever a *module* is meant. **Never "the emulators" for the project** — that phrase belongs to the `:emulators` module, and it reads as the product elsewhere, so every sentence carrying both would need disambiguating.

**Personas.** Two distinct audiences; docs and decisions should be clear about which they address.
- **Migrator**: the programmer using SB-Emulators to port their Swing app onto Vaadin — consumes `:emulators` / `:surrogates` as a dependency, does the import-swap, runs their app in the browser. The migrator is SB-Emulators' *user*; **"user code"** throughout these docs means the migrator's code. README.md is migrator-facing.
- **Maintainer**: the programmer developing SB-Emulators itself — works inside this repo, reads the decision logs, runs the generator, adds emulators/surrogates. DEVELOPING.md and the `*/decisions.md`, `*/architecture.md` docs are maintainer-facing. Project-internal scope and sequencing are maintainer concerns — keep them out of migrator-facing docs.

**This file (`CLAUDE.md`) is agent-first** — the project brief Claude loads every session; humans are welcome readers, but the maintainer-human home is DEVELOPING.md. When content would read differently for a human maintainer than for the agent, the human-shaped version goes to DEVELOPING.md; CLAUDE.md keeps what makes the agent act correctly. Most content serves both and needn't be split — DEVELOPING.md points into CLAUDE.md for shared facts rather than restating them. **`AGENTS.md` is a byte-identical copy of this file** for the tools that read that name — a real file rather than a symlink, because a default Git-for-Windows checkout turns a symlink into a one-line text file — and `AgentsBriefTest` fails the build when the two differ: edit here, then copy over `AGENTS.md`.

- **Import-swap drop-in**: the migration *technique* — users rewrite `javax.swing.*` → `vaadinx.swing.*` imports and recompile. Not binary-compat — we do not shadow the JDK's `javax.swing` module. Compiled Swing jars need recompilation.
- **Emulator**: a `vaadinx.awt.Component` / `vaadinx.swing.*` class — the faithful reproducer of the corresponding JDK Swing/AWT class's API behavior. The word matches the project's framing ("runtime emulation of the Swing API"): the emulator class stores Swing-side state, fires Swing events, and drives a Vaadin peer underneath so the user sees a Swing JButton and the browser sees a Vaadin Button. Pairs with **peer**: every emulator holds one peer via has-a composition, every registered peer resolves back to one emulator via `EHelper.getEmulator(peer)`. Not "wrapper" (misframes as wrapping); not "shim" (misframes as glue-between — the emulator *is* the Swing API surface, not a layer between user code and it).
- **Peer**: the underlying Vaadin `Component` that backs an emulator. Borrowed from AWT's original `java.awt.peer.*` terminology — Vaadin plays the role that native widgets played for AWT.
- **Bootstrap** vs **host app** — two referents, never drifted together ([M1D_bootstrap_choice](./migration/1-swing-to-emulators/decisions.md#M1D_bootstrap_choice)). *The bootstrap* is the library that starts the servlet container and hands Vaadin its request threads — Spring Boot or Vaadin Boot. *The host app* is the scaffold a migrated app's views live in (`Main`, `AppShell`, `AppRoute`, …), shipped per bootstrap as a seed under `guides/1-swing-to-emulators/seed/`. Not "the Boot": that both options are named Boot is a coincidence a third lane (a WAR, with no Boot) breaks. The shared guide names neither bootstrap.
- **Surrogate**: a class in `:surrogates` that extends a Vaadin component directly (is-a), reproducing full Swing-behaviour coverage for one specific component. Used as the peer by the matching emulator once available. A surrogate is always a valid peer type — pairs with **emulator** via has-a composition.

## Migration arc

A Swing app's migration to native Vaadin proceeds through four stages, two of which are in scope for this project:

1. **Original Swing app** (out of scope — pre-migration starting point).
2. **Emulator stage.** Mechanical import-swap (`javax.swing.*` → `vaadinx.swing.*`); recompile against `:emulators`; the app runs in the browser. Code shape stays Swing-shaped; styling/UX iteration can begin. `:emulators` is the API surface here. Value prop: cheapest path from "Swing desktop app" to "running web app" — mostly-mechanical rewrite, not weeks of redesign.
3. **Surrogate stage.** View-by-view, `:emulators` views rewrite to `:surrogates` directly. Code shape becomes Vaadin-shaped, with Swing-flavoured helpers where R_vaadin_first allows. `:surrogates` is the API surface for rewritten views; views the migrator hasn't reached yet keep running on `:emulators`. The two coexist *across* views; **per-view, code is at one layer — `:emulators` and `:surrogates` APIs are not mixed within a single view's code-base.** Value prop: gradual transition with familiar Swing idioms still available where Vaadin doesn't directly cover them.
4. **Pure-Vaadin stage** (out of scope — final rewrite from `:surrogates` toward stock Vaadin components; project's job is done by here).

**Local-LLM stage-2 target (aspirational, under exploration — not decided).** Keep at the back of your head when shaping emulator/migration design: we *try* to make the stage-2 swing→emulators port achievable by a **local** LLM (~35B-A3B MoE / ~30B dense, wired to LSP + Vaadin/Maven MCPs), not a cloud model — the motivation is privacy-conscious enterprises whose source can't leave their premises. The lever is faithful emulators lifting the heavy work off the agent so the port stays mechanical. It's a *try*, with escape hatches (revisit-and-relax, or a small human-ported "island" residue), and test generation is explicitly out of this target for now. Full framing + open questions in [#21](https://github.com/vaadin/swingbridge-emulators/issues/21); to be brainstormed in a dedicated session.

The two-subproject split (`:emulators` has-a Vaadin peer; `:surrogates` is-a Vaadin component, per [D_emulator_surrogate_split](./emulators/decisions.md#D_emulator_surrogate_split)) maps directly onto stages 2 and 3: **`:emulators` is the stage-2 API; `:surrogates` is the stage-3 API**. Several design decisions encode the layering implicitly — emulator public API stays JDK-faithful (R_swing_is_truth + a stage-2 user expects a Swing-app shape: emulator `JButton.getIcon()` returns `javax.swing.Icon`, emulator `JComponent.getTopLevelAncestor()` walks the emulator container hierarchy); surrogate public API stays Vaadin-shaped (R_vaadin_first + a stage-3 user expects a Vaadin component with Swing-flavoured helpers: SJButton's inherited `getIcon()` returns Vaadin `Component`, `JComponentMixin.getTopLevelAncestor()` walks the Vaadin parent chain per [SD_top_level_ancestor](./surrogates/decisions.md#SD_top_level_ancestor)). Apparent two-layer artefacts (`vaadinx.awt.event.ComponentEvent` vs `SComponentEvent`, parallel `EHelper.callSwing` / `SHelper.callSwing` impls per [SD_sframe](./surrogates/decisions.md#SD_sframe)) are stage-divergence, not API confusion: per-view single-layer code never sees both at once, and the import-rewrite at the stage-2→3 boundary IS the migrator's "I'm changing layers" prompt.

## Subprojects: `:emulators`, `:surrogates`, `:emulators-printing`, `:emulators-spring`, `:migration-annotations`, `:migration-guardrails`, `:migration-tool`, and `:zip-distro`

Eight Maven modules with complementary stances:

- **`:emulators`** — `vaadinx.awt.*` / `vaadinx.swing.*` classes that reproduce the Swing API surface faithfully (has-a Vaadin peer). 100% API compatibility, best-effort behaviour. This is the import-swap target user code compiles against.
- **`:emulators-printing`** — optional add-on: the virtual PDF printer (`vaadinx.awt.print.PrinterJob`, [D_printing](./emulators/decisions.md#D_printing)). Separate module so its PDFBox dependency stays off non-printing migrators' classpaths (D_pure_java_artifact); depends on `:emulators`.
- **`:emulators-spring`** — optional add-on: the host-app wiring a migrated app needs **on Spring Boot**, per [D_library_servlet](./emulators/decisions.md#D_library_servlet). `vaadinx.swing.app.spring.SwingBridgeSpringServlet` is the `SpringServlet` whose session lock is virtual-thread-aware (the Spring twin of `:emulators`' `SwingBridgeVaadinServlet`, reproduced rather than inherited because Java has one superclass), and `SwingBridgeAutoConfiguration` registers it *and* `SwingBridgeEmulatorsBootstrap` — so **declaring this coordinate is the whole of the Spring lane's wiring**: no servlet, no `ServletRegistrationBean`, no bootstrap bean in the migrator's source. **This is the one place in SB-Emulators that self-registers**, under [R_no_spi_selfregister](#hard-rules)'s framework-dedicated-module exception, whose three limbs shape the class: dedicated module, Spring's own discovery rather than `META-INF/services`, and every bean `@ConditionalOnMissingBean` so an app declaring its own still wins. It is also **the only module in the reactor that may take a Spring dependency**, which is what finally gives the Vaadin-resolves-Spring-Boot-4/Framework-7 version-drift gate a durable home (`SpringVersionDriftTest`) — before it, that check could only live in a testapp every round rewrites. Depends on `:emulators` + `vaadin-spring`; nothing depends back on it.
- **`:surrogates`** — classes that extend Vaadin components directly (is-a) to reproduce full Swing functionality for a given component. 100% functionality coverage, narrow surface. `:emulators` depends on `:surrogates` and uses a surrogate as the peer once one exists for a given component.
- **`:migration-annotations`** — `com.vaadin.swingbridge.migration.IntentionallyStatic`, the allowlist marker for the static sweep's build gate, whose javadoc is the canonical definition of that gate's rule ([M1D_static_sweep_allowlist](./migration/1-swing-to-emulators/decisions.md#M1D_static_sweep_allowlist)). Carried by *migrated app* source, not by SB-Emulators'. **Zero dependencies is the module's contract, not tidiness:** a migrated app's UI-free service modules annotate their allowlisted statics too, and M1D_static_taxonomy's Step 0 classifies a module UI-bearing if it depends on one that is — so a Vaadin dependency here would invert the classification the sweep rests on. Nothing in SB-Emulators depends on it, except `:migration-guardrails`, which points *at* it and never back.
- **`:migration-guardrails`** — `com.vaadin.swingbridge.migration.guardrails.MigrationGuardrails`, the stage-2 guide's Phase 6 step 6 as one class a *migrated app* calls from its own test suite: `new MigrationGuardrails("com.myapp").allowSystemExitInMainMethods().run()` checks all three gates (every static provably immutable or `@IntentionallyStatic`; no component in a static field; no JVM exit) and reports every violation in one failure. Per [M1D_guardrails_artifact](./migration/1-swing-to-emulators/decisions.md#M1D_guardrails_artifact). **ArchUnit is the engine and stays private** — the migrator imports one SB-Emulators type and no `com.tngtech.*`, so SB-Emulators' ArchUnit version is not a compat surface on their build — and it is **test-scope by consumption**, so nothing here reaches their runtime. The class is a **facade over `:migration-tool`**, which owns the rule engine and the ArchUnit dependency, so this gate and the tool's `StaticSweep` worklist answer one question with one implementation ([`Q_one_rule_engine`](./migration/1-swing-to-emulators/decisions.md#M1D_static_sweep_tool)). The split that matters is the terminal: `StaticSweep` prints and exits 0 (a non-empty worklist mid-migration is the expected state), this **throws** — which is what makes the sweep stay done afterwards. **No compile-scope dependency on `:emulators` or anything Vaadin, and for `:migration-annotations`' reason rather than tidiness:** the two component types are matched **by name** (`vaadinx.awt.Component`, `com.vaadin.flow.component.Component`), so a UI-free service module can install the guardrails without a Vaadin dependency flipping its M1D_static_taxonomy Step 0 classification — and in such a module the names resolve to nothing and the rule trivially passes. The by-name match is also what makes the module **permanent rather than stage-2**: at stage 4 `vaadinx` is gone and both remaining gates are still Vaadin hygiene. Every relaxation names its target (`allowSystemExitInMainMethods()`, `allowSystemExitIn(String...)`) — there are no global off-switches, and the static gate has no relaxation at all because `@IntentionallyStatic` is already its per-field hatch. `:emulators` is a *test*-scope dependency here, for the fixtures only.
- **`:migration-tool`** ([README](./migration-tool/README.md) — invocations, example reports, what each tool declines to do) — the runnable jar an agent following the stage-2 guide points at a Swing app, carrying **one `main` per mechanical phase of that guide**. None carries compiled-in knowledge of Swing: the two source tools read a tab-separated table off their classpath, and `StaticSweep` reads the app's own class files, where the compiler already resolved everything it asks about. **One module-wide consequence of that third main: `<maven.compiler.release>` here is 24, alone in the reactor** — `java.lang.classfile` does not exist below it — which costs nothing downstream because the jar is *run*, never compiled against, and JDK 24+ is already the project's floor. **No dependency on `:emulators`, `:surrogates` or anything Vaadin, and for the same reason as `:migration-annotations`' contract rather than tidiness:** the tables travel with the jars, where reflecting over `:emulators` instead would drag Vaadin onto the tool's classpath and hide them behind a build. (This was written as "zero runtime dependencies" until [`Q_one_rule_engine`](./migration/1-swing-to-emulators/decisions.md#M1D_static_sweep_tool) read the reason back: "zero" was a proxy, and an ordinary third-party library — ArchUnit, once the static-sweep rule engine consolidates here — hides no table and changes no module's Step-0 classification. The bar stays high, since each entry costs the `-cp` invocation another jar; it is just weighed against the reason.) The module also **packages itself as a distribution zip** (`bin/` + `lib/`, attached as the `dist` classifier so it installs and publishes with the module, per [D_kit_tool_zip](./emulators/decisions.md#D_kit_tool_zip)) — that zip is what `:zip-distro` unpacks into the kit's `tools/`, and it is a one-line answer for a migrator who came by coordinate. The zip carries the **engine only**: whoever assembles a classpath drops the table jars into `lib/`, which is what keeps this module free of `:emulators`. The mains are finders/assistants that **exit 0 whenever they ran** — output is for the agent to triage, never a gate — and are invoked through `bin/`, which is `-cp` and a class name, never `java -jar` (which ignores `-cp` and would leave the tables invisible; `ImportSwap` with no table on its classpath **exits 2 naming the fix**, so a missing table is loud rather than a rewrite of nothing reported as success). **These contracts are per entry point, not per module:** `com.vaadin.swingbridge.migration.tool.guardrails.GuardrailEngine` + `ImmutableTypes` live here too — the rule engine `:migration-guardrails` fronts — and its `violations()` judges nothing while the facade's `run()` throws.
    - **`com.vaadin.swingbridge.migration.tool.importswap.ImportSwap`** (Phase 2) rewrites imports (every wildcard shape) *and* in-code fully-qualified references onto their emulators, per [M1D_import_swap_tool](./migration/1-swing-to-emulators/decisions.md#M1D_import_swap_tool). Its table is `META-INF/emul/ported-types.tsv`, unioning core's copy with each add-on's so core still never learns add-ons exist. Core's is a **golden file** regenerated and diff-checked by `emulators/.../PortedTypesTableTest` (a new emulator reddens the build until regenerated with `-Demul.regenerate=true`); each add-on's is **declared** and guarded by its own `PortedTypesTableTest`, because an add-on replaces its upstream so there is nothing to reflect against. Token-level by design — no AST, no LSP — and it declines rather than guesses: an unreadable import or an ambiguous simple name leaves the file untouched with a reason in the Markdown report. Scope is what the table plus a file's own imports decide; `System.exit` routing, the static sweep and every other judgement call stay with the agent.
    - **`com.vaadin.swingbridge.migration.tool.hazardscan.HazardScan`** (Phase 1) finds [spec.md §7](./migration/1-swing-to-emulators/spec.md)'s migration hazards plus the two §5 import sharp edges, per [M1D_hazard_scan_tool](./migration/1-swing-to-emulators/decisions.md#M1D_hazard_scan_tool). Its table is `META-INF/emul/hazards.tsv` (core's copy is this module's own resource, unioned across the classpath the same way, so an add-on *could* contribute a grep-shaped watch-out; none does yet). **Every hazard carries an `H_` slug in exactly two places** — an `<a id="H_…"></a>` on its spec.md bullet and the tsv's first column — and `HazardTableTest` joins them in both directions, so editing a pattern without editing the spec bullet (or the reverse) reddens the build. It replaced a checked-in `hazard-scan.sh`, whose patterns were a second hand-synced copy that had already drifted. Hazards with no scan signal are `manual` rows that render as a closing checklist; clean sections are printed, not omitted, so the report is the phase's worklist.
    - **`com.vaadin.swingbridge.migration.tool.staticsweep.StaticSweep`** (Phase 1 / [static-fields.md](./guides/1-swing-to-emulators/static-fields.md) Step 1) builds the `static`-field worklist from the **pre-swap class files**, per [M1D_static_sweep_tool](./migration/1-swing-to-emulators/decisions.md#M1D_static_sweep_tool). **It has no table** — a Swing app under migration builds by definition, so `java.lang.classfile` plus `Class.forName(name, false, loader)` read what the compiler already resolved: field tables and `Signature` attributes for the kinds and declared types, `getstatic` / `putstatic` operands (which *name* the field, and say read or write, with a line) for the writers/readers and for `Q_method_or_type`, `RuntimeInvisibleAnnotations` for `@IntentionallyStatic`, and the JVM's own resolver for `Q_component` up the whole hierarchy. Nothing in the app runs (`initialize = false`), a type that will not load is reported **unresolved** and never demoted, and `--diff <stage-2-classes>` gives every stage-1 row a fate (*gone* / *made a constant* / *annotated* / **still unvetted**) — [former-singletons.md](./guides/1-swing-to-emulators/former-singletons.md)'s closing check as a diff. It shares one rule engine with `:migration-guardrails` (`ImmutableTypes`, per `Q_one_rule_engine`) and differs only at the terminal: it prints and exits 0, the gate throws. **What it leaves is the verdicts** — which `Reason` a row claims, session vs tab scope — measured at three real decisions out of thirteen routed rows on inventory.
- **`:zip-distro`** — assembles the **distribution kit**, `swingbridge-emulators-<version>-dist.zip`: one download a stranger unzips and runs a Swing→emulators migration from, without cloning this repo. It ships the `guides/` tree, a `tools/` folder holding `bin/` + `lib/` unpacked from `:migration-tool`'s own distribution zip, the migrator-facing agent prompt, three Claude Code skills — one migrate command per shape (`/migrate-testapp <app>`, `/migrate-your-app` for the `your-app/swing/` slot, `/migrate-swing-app <folder>` in place), each of which **does the migration in its own session — no subagent** ([D_kit_no_subagent](./emulators/decisions.md#D_kit_no_subagent)), because a spawned agent works where the user cannot watch it and reports back a summary; there was a fourth, `/lsp-preflight`, until the language server stopped being a gate ([M1D_lsp_recommended](./migration/1-swing-to-emulators/decisions.md#M1D_lsp_recommended), retiring [D_kit_lsp_preflight](./emulators/decisions.md#D_kit_lsp_preflight)) — a `your-app/swing/` slot for the customer's own app ([D_kit_your_app_slot](./emulators/decisions.md#D_kit_your_app_slot)), and three example apps off `testapps/` (`inventory` on its author's terms, with its `PROVENANCE.md` as the licence lane, per [D_kit_what_ships](./emulators/decisions.md#D_kit_what_ships)). **The only jars it ships are swap tables** — `:emulators` and both add-ons land in `tools/lib/` because `ImportSwap` unions their `META-INF/emul/ported-types.tsv`; the *migrated app* still resolves SB-Emulators by coordinate everywhere (Central for a release, `~/.m2` for a development kit), and nothing in any shipped pom points at `tools/lib/`. The kit **mirrors this repo's geometry exactly**, which is load-bearing: it is what lets every link in the shipped docs stay relative, and it is why `guides/` sits at the repo root rather than under `migration/`. Two gates fall out and are worth knowing before editing any migrator-facing doc: **a file under `guides/` may only link to what the kit ships** (`:emulators`' `GuideLinkScopeTest` from the repo side, `:zip-distro`'s `KitLayoutIT` from the shipped side), and an unfilled slot ships as `<filename>.placeholder` with exactly one of the pair present. The default build assembles and runs every check in seconds — including `KitSmokeIT`, which runs a shipped launcher over a shipped app and needs no network — while `-Pkit` (what CI runs) adds only the invoker run building every shipped testapp stage. Full rationale, including why the tools became a zip of their own and why the testapps left the reactor: [D_distribution_zip](./emulators/decisions.md#D_distribution_zip).
- **The blocking-dialog machinery is a dependency, not a module**: [vaadin-blocking-dialogs](https://github.com/mvysny/vaadin-blocking-dialogs) (`UIFibers`, the runner-neutral API) plus `vaadin-uifiber-loom` (the virtual-thread runner, `VirtualThreadAwareLock`), Apache-2.0, pinned exactly at a 0.x version from Maven Central — pre-1.0, it breaks APIs freely. It lets `vaadinx.EHelper.callSwing` park modal Swing dialogs without blocking the Vaadin request thread, per [D_callswing_loom](./emulators/decisions.md#D_callswing_loom) and [D_blocking_dialogs_library](./emulators/decisions.md#D_blocking_dialogs_library). `:emulators` depends on it; `:surrogates` does not (per [SD_sframe](./surrogates/decisions.md#SD_sframe) the surrogate-side `SHelper.callSwing` stays inline). **Every park SB-Emulators makes goes through `UIFibers.parkAndAwait`** (`EHelper.awaitModal` / `awaitBrowserRoundTrip`) — never a bare `future.get()` / `latch.await()` inside a fiber, which the runner deliberately holds the session lock through — and **no monitor is held across one**: a second fiber of the session entering that monitor would keep the session lock while waiting, and the session freezes (the one place the runner's rule departs from Swing, whose single EDT re-enters its own monitors).

**Third-party library add-ons** live in `third-party/`, one Maven module per forked library, and are *not* part of the four above: each provides one third-party Swing library's API on top of `:emulators` so a migrated app's `com.jgoodies.` / `com.toedter.` imports rewrite to `vaadinx.jgoodies.` / `vaadinx.toedter.` and keep compiling. They depend on `:emulators` (+ `:surrogates` when they need a peer) and **nothing in SB-Emulators core knows they exist** — that one-way direction is the property the add-on model is testing, so a core change made to accommodate an add-on is a finding, not a chore. `artifactId` carries the *upstream* version (`swingbridge-emulators-jcalendar-1.4` — which API surface you get), `<version>` carries SB-Emulators' (the add-on's own release train). **Each add-on carries the licence of the upstream library whose API it reproduces, fork or reimplementation alike** ([M1D_addon_upstream_licence](./migration/1-swing-to-emulators/decisions.md#M1D_addon_upstream_licence)) — so neither is under the project licence and each ships its own `LICENSE` into its jar's `META-INF/`. In the jcalendar tree the GPLv2+CE header is a *build failure* rather than a cosmetic slip, gated by `LicenseHeaderTest` rule 5: LGPL-2.1 §3 permits relicensing to the ordinary GPLv2 but not to GPLv2+CE, since the Classpath Exception grants a linking permission over code that is not ours. (The jgoodies fork needs no such gate — its files keep upstream's own headers.) Two exist: `swingbridge-emulators-jcalendar-1.4` (a clean reimplementation of `JDateChooser` over `SJFormattedDatePicker`, **LGPL-2.1** — upstream JCalendar's licence, taken although the module copies nothing) and `swingbridge-emulators-jgoodies-forms-1.2.1` (a BSD fork — 17 of upstream's 36 files, with `FormLayout`'s pixel engine replaced by a `CssEmittingLayoutManager` emitting CSS Grid, and the `FontMetrics`/`Toolkit` unit converter replaced by a font-relative CSS one). **Each add-on ships its own migrator-facing `MIGRATION.md`** (module root, and inside the jar at `META-INF/emul/MIGRATION.md`), indexed from [guides/1-swing-to-emulators/addons.md](./guides/1-swing-to-emulators/addons.md) — core holds the index only, and a per-module `MigrationDocTest` fails the *add-on's* build if the index forgets it, so the one-way direction holds for docs as well as code. **Status: both are starter prototypes, shipped as-is and frozen at what they cover** — no widening is planned, so widening requests are parked; bugfixes are not, per [M1D_addon_starter_status](./migration/1-swing-to-emulators/decisions.md#M1D_addon_starter_status), which also lists every migrator-facing place that states the status and must change together if that ever changes. Packaging model: [M1D_addon_packaging](./migration/1-swing-to-emulators/decisions.md#M1D_addon_packaging); the swap-vs-reimplement triage rule and the two ports: [M1D_swap_vs_reimplement](./migration/1-swing-to-emulators/decisions.md#M1D_swap_vs_reimplement); the addendum + index contract: [M1D_addon_migration_docs](./migration/1-swing-to-emulators/decisions.md#M1D_addon_migration_docs). Per-module licence lane: each module's `PROVENANCE.md`.

**Surrogates evolve in concert with emulators; a new emulator requires a surrogate first, and the surrogate must be fully implemented within R_vaadin_first's cap before the emulator is built over it.** `:surrogates` picks the next surrogate on its own priorities (coverage value, reuse potential, design readiness). No parallel deferred-list: surrogate gaps are either closed or properly classified per R_match_swing_errors / D_gap_severity_triage (sub-bucket (a)/(b)/(c)), never carried as "we'll get to it." See D_emulator_surrogate_split for the original split rationale and [D_surrogate_first](./emulators/decisions.md#D_surrogate_first) for the surrogate-first ordering policy.

## Hard rules

Rules are identified by slug (`R_swing_is_truth`), as decisions are; old `R1`–`R13` numbers map at [DECISION-ID-MAP.md](./DECISION-ID-MAP.md).

1. <a id="R_pure_java_library"></a>**R_pure_java_library. Library code (`src/main`) is pure Java.** No Kotlin in the library.
2. <a id="R_java_karibu_tests"></a>**R_java_karibu_tests. Tests are Java + Karibu-Testing** under `src/test/java`, driving Karibu through its `LocatorJ` static API. Karibu reaches through the `peer` field since peers are real Vaadin components. **Every test in the repo is Java and no module carries a Kotlin toolchain** — [D_kotlin_retired](./emulators/decisions.md#D_kotlin_retired) retired the original mixed-language corpus, superseding [D_tests_in_java](./emulators/decisions.md#D_tests_in_java)'s decision (not its rationale). One consequence of that rule outlives the mixed lane and is worth keeping explicit, because it is what a future "just write it in X" would break: **a test whose claim is "migrated Java source still compiles and resolves this way" must be Java**, since another language's resolution rules are not javac's and a green suite in one only exercises the bytecode surface (`emulators/src/test/java/vaadinx/swing/text/html/HTMLEditorKitJavaCompatTest.java` is the worked example — the claim it defends is inexpressible in Kotlin). **Shared test infrastructure — base classes, fixtures, helpers — is ordinary Java like everything else**, and no longer needs the lane rule that once forced it there.
3. <a id="R_match_swing_errors"></a>**R_match_swing_errors. Error handling: match Swing's error handling.** When real Swing/AWT throws on given inputs (bad index into `getComponent(int)`, adding a component to its own ancestor, `setValue(null)` on a `SpinnerNumberModel`-backed spinner, …), we throw too using the same exception type — swallowing programming errors hides real bugs. **Incomplete emulation splits by severity:** *minor* gaps WARN-and-continue via `vaadinx.EHelper.onUnimplemented(className, method, args)` — logs WARN via slf4j, returns a sensible default, never throws; doing something silly beats crashing the host app. Minor gaps fall into three sub-buckets per D_gap_severity_triage: (a) *blocked-upstream* (we'd implement if upstream landed the API; e.g. SJSlider ticks behind vaadin/flow-components#9181); (b) *permanently-deferred-by-policy* (out of project scope; e.g. user-authored `Graphics` paint, JTable cell editors as faithful in-cell swap, JApplet, L&F dispatch); (c) *R_vaadin_first drop-and-WARN* (no Vaadin counterpart for the JDK contract and round-trip alone isn't a goal; e.g. AbstractButton state-conditional icon setters, alignment, visual flags) — **surrogate-side; on the emulator side R_decline_effect_only applies instead**, so what gets dropped is the effect while the state and the event fan-out stay. The triage baseline for whether something belongs in (b) — "intentionally deferred" rather than "we'll get to it" — is a **typical CRUD app** (list view + detail form + dialogs + menubar), not Sampler's exhaustive testbed scope. The **major-gap throw trigger is an enumerated set of specific cases** (ten today; future additions land case-by-case): (1) loom rescue of a Swing-deadlock — canonical: `SwingWorker.get()` from the EDT, `invokeAndWait` from the EDT; (2) `EXIT_ON_CLOSE` close-attempt on a JFrame — log-and-noop is rejected as silent ignoring of program-lifetime intent; (3) `Date↔LocalDate` conversion via `SHelper.toLocalDate` / `SHelper.toDate` (used by `SJSpinner` SpinnerDateModel and `SJFormattedDatePicker`) when `BrowserTimeZone.fetch()` was not called from a UI init listener — programming-error contract per [SD_browser_timezone](./surrogates/decisions.md#SD_browser_timezone), since a silent UTC fallback produces dates an hour off in subtle ways while the migrator's wiring oversight is a one-line fix; (4) `JFileChooser.showDialog(parent, text)` — `CUSTOM_DIALOG` declares no LOAD/SAVE direction, and in a browser the two are different mechanisms that must be picked *before* the dialog opens, so no continuation is defensible from SB-Emulators' vantage point (the same shape as case (3): a silently-wrong default vs. a mechanical one-line fix at the call site), per [D_showdialog_throws](./emulators/decisions.md#D_showdialog_throws); (5) a `MainWindowRoute` attaching on a UI where `vaadinx.swing.app.SwingBridgeEmulatorsBootstrap` never ran — the app forgot the one SPI line, and three separate late failures (a date input throwing, focus silently wrong, no shutdown on tab close) collapse into one early one at the route, per [M1D_bootstrap_canonical](./migration/1-swing-to-emulators/decisions.md#M1D_bootstrap_canonical); (6) a deployment on a JDK older than 24, refused by `SwingBridgeEmulatorsBootstrap.assertSupportedRuntime` at servlet init (the loom runner's own constructor accepts 21–23 behind a system property SB-Emulators never sets) — the same shape as (5) one layer down: a deployment-configuration error where every later modal dialog would instead hang as a pinned-carrier deadlock with no stack trace, no WARN and nothing to grep for, so three hours of jstack collapse into one message at startup (the enforcer gates the *build* at `[24,)`; an app built on 24 and deployed on 21 passes every gate); (7) a window shown or hidden (`vaadinx.awt.Window.setVisible` → `EHelper.runInUIThread`, the one peer write that cannot wait for its peer to get a UI) from a thread carrying **no `EmulatorContext`** — an ordinary peer write needs no context, since it queues until its peer has a UI ([D_lazy_peers](./emulators/decisions.md#D_lazy_peers)) — a plain `Thread` or an unwrapped executor, fixed by one line at the *submit* site (`EmulatorContext.wrap(executor)` / `ctx.run(...)`), which is why the throw beats a WARN at the write: the defect is in another file, and a dropped push is invisible from the Swing side since the state is stored and the event fired, per [D_no_context_throws](./emulators/decisions.md#D_no_context_throws); (8) a **blocking** emulator call — a modal `Dialog.setVisible(true)` and everything composing one (`JOptionPane.show*`, `JFileChooser.show*`, `JColorChooser.showDialog`) — that cannot reach a live UI to show on, or whose wait nobody will answer any more — a background thread's park interrupted, a UI fiber's park ended by its dialog's detach at a tab close or session destroy — throwing `vaadinx.BrowserSessionClosedError` per [D_modal_from_background](./emulators/decisions.md#D_modal_from_background) (the UI-fiber leg ends the fiber quietly at `callSwing`'s root, [D_blocking_dialogs_library](./emulators/decisions.md#D_blocking_dialogs_library)); the browser round-trips `EHelper.awaitBrowserRoundTrip` serves (preferences, clipboard, client details) throw it the same way, and so does a background thread's `SwingUtilities.invokeAndWait` when the session has no live UI to run it on ([D_invoke_from_background](./emulators/decisions.md#D_invoke_from_background)); (9) a deployment whose `VaadinService` never routed `getSessionLock()` through `com.github.mvysny.blockingdialogs.uifiber.loom.VirtualThreadAwareLock.wrap()`, refused by the loom runner's `SessionLockCheck` at each session's first request — case (6)'s shape one wiring line over: without the wrapper a virtual thread that takes the session lock deadlocks its session with no message, per [D_vt_aware_session_lock](./emulators/decisions.md#D_vt_aware_session_lock). The throw is the library's and an `Error`, since Vaadin only logs a session-init listener's `Exception`; (10) a deployment that handles Vaadin requests on **virtual threads** (`spring.threads.virtual.enabled=true`; Vaadin Boot pins `useVirtualThreadsIfAvailable(false)`), refused by `EHelper.callSwing` at the first peer→Swing callback (and, on the Spring Boot lane, already at context refresh by `:emulators-spring`, which can read the property) — the loom runner supports platform request threads only, and the sting is that `Thread.isVirtual()` cannot distinguish the container's request thread from one of our own UI fibers, so before this case the re-entrancy fast path absorbed it: no fiber, no access-queue drain, no epilogue, state left unsettled with no WARN and no stack trace (the fast path now asks `UIFibers.isInUIFiber()`). The discriminator is a current `VaadinRequest`, which is what separates the container's thread from the migrator's own background VT — where inline dispatch is correct and [R_tolerate_off_ui_thread](#R_tolerate_off_ui_thread) forbids inventing a throw. Per [D_virtual_request_threads](./emulators/decisions.md#D_virtual_request_threads). The axis is not *"is this write cosmetic"* — that taxonomy is unfinishable — but *"does the calling method afterwards block on a browser round-trip?"*, which SB-Emulators decides for itself and whose answer-set is small and closed. For those callers alone, degrading is not a degradation but an indefinite hang on a latch nothing can count down. **This case is the list's one deliberate deviation from the `IllegalStateException` fallback below**: `showConfirmDialog` must return an `int` and there is none to return, and only an `Error` survives the `catch (Exception e)` that migrated worker bodies are full of — an `AWTError`, since that is already this layer's Error. **The other two no-UI legs stay soft** — a closed tab and a session invalidated mid-wait are races with the browser, not configuration errors, and keep dropping the effect for every *non-blocking* caller. Throw the same exception type Swing would throw under the equivalent observable failure where applicable, `IllegalStateException` with a pointer-at-cause message otherwise. Observable-state divergence outside the enumerated cases (R_layouts_close_enough layout close-enough, dummy bounds, R_vaadin_first drop-and-WARN, blocked-upstream visual flags) stays under the WARN umbrella — those are minor gaps, not major. See D_never_fail_on_gaps, D_gap_severity_triage.
4. <a id="R_best_effort_behaviour"></a>**R_best_effort_behaviour. Behavior compatibility is best-effort.** Target: "close enough to run a typical Swing app." Not bug-for-bug Swing semantics. **This licenses falling *short* of what the JDK does — never inventing what it does not do.** "Not bug-for-bug" excuses an approximation we could not deliver exactly; it is not a warrant to correct a JDK behaviour we find unhelpful, which is [R_no_silent_improvements](#R_no_silent_improvements)'s territory (read the two together — this rule is the downward cap, that one the upward). The distinction is not academic: [SD_sjpasswordfield](./surrogates/decisions.md#SD_sjpasswordfield) cited this rule's last sentence to decline matching a JPasswordField "misbehaviour" that did not exist, and shipped a `getText()` that masked passwords for four months. **Before invoking this rule to diverge, establish what the JDK actually does — by running it, not by recalling it.**
5. <a id="R_layouts_close_enough"></a>**R_layouts_close_enough. Layouts are close-enough — but only *cosmetically*.** "Close-enough" scopes over *pixel-level* divergence: a component a few pixels off its Swing position, a font that isn't the exact family/size, padding/gaps that don't match to the pixel. Those are acceptable and stay acceptable — no pixel-accurate layout library is planned ([D_pixel_layout_not_planned](./emulators/decisions.md#D_pixel_layout_not_planned)). It does **not** license *structural* layout failure: a resizable component rendering at preferred width instead of filling its region (leaving half the dialog empty), children stacked horizontally when the layout is vertical (or vice-versa), content wrapping when it should fit on one line, or a component landing in the wrong region. Structural correctness — the right components in the right regions, filling/stretching as the `LayoutManager` dictates — is in scope and must be right; only the last mile of pixel/font fidelity is deferred.
6. <a id="R_infra_not_surface"></a>**R_infra_not_surface. Build infrastructure correctly; don't expand surface area preemptively.** When you touch a mechanism (event dispatch, layout, focus, painting), implement it generally and properly — half-done infrastructure costs more to finish later than to do right the first time. But don't start on components, listener types, or features the current slice doesn't exercise; generated stubs stay stubs until needed. Still generate code that calls those stubs (e.g. even if we know LayoutManager is null, copy code from Swing which calls it).
7. <a id="R_swing_is_truth"></a>**R_swing_is_truth. Swing compat layer is the source of truth.** When implementing a Swing method, replicate its original behaviour as closely as possible — store fields, fire Swing events, walk parents — *and* drive the Vaadin peer to match. When the peer changes on its own (user types, clicks, focuses), subscribe to the peer's event, update the Swing-side field, then fire the corresponding Swing event. User code always sees consistent Swing state and gets the events it expects. Guard against feedback loops in two layers. **First, a peer listener filters on `isFromClient()`** wherever its event carries the flag (value-change, click, focus, blur): a server-originated peer event is our own write's echo or the surrogate rendering the emulator's model, never news to the emulator — so a state change Vaadin makes server-side on its own goes unheard, and the emulator computes that change the JDK's way instead ([D_lazy_peers](./emulators/decisions.md#D_lazy_peers) rule 10). **Behind it, a `preventPeerEvents` flag**, which a DOM-event listener (no server origin) relies on alone: set it *inside* the `withPeer` body that writes, never around the `withPeer` call — around it, the flag is cleared before a queued write drains (rule 1); in the peer listener, bail out if the flag is set; clear it in a `finally`. **Read the flag in the listener body itself, before entering `EHelper.callSwing` — not only inside the callback.** The echo of our own write-through is not peer→Swing work at all, so it should never reach the R_callswing_envelope envelope: `callSwing` throws when no UI is current, which turns an echo that ought to be ignored into a hard failure (measured 2026-08-21 — a modal cell editor's parked commit resumed on a queue-drain thread with no current UI and a JTextField's own `setText` push blew up). The guard inside the sync method stays as defence in depth for its other callers. Update the Swing-side field *before* pushing to the peer, so the listener's view of "current state" is already correct. An equality check on old vs. new is a useful happy-path optimization (and essential for value-carrying events like document changes) but is not a substitute — listeners without a prior value to diff (e.g. `ActionListener` on button click) have no defense without the flag. Exempt: layout and painting — neither maps cleanly onto Vaadin/DOM and both are best-effort per R_best_effort_behaviour / R_layouts_close_enough.
8. <a id="R_callswing_envelope"></a>**R_callswing_envelope. Peer → Swing callbacks funnel through `EHelper.callSwing`.** Every Vaadin peer listener whose job is to fire a Swing-side event (click, value-change, focus, window-close, …) wraps its body in `EHelper.callSwing(Runnable)`. As of [D_callswing_loom](./emulators/decisions.md#D_callswing_loom), `callSwing` runs each call as a UI fiber — a virtual thread, via vaadin-blocking-dialogs' `UIFibers.runUntilPark` — and drains the session's access queue synchronously, so blocking modal dialogs (`JOptionPane.showMessageDialog`, `dialog.show()`) can park without blocking the Vaadin request thread, and cascading fan-outs settle before the next user action. 100% coverage matters: one listener that calls `fire*` directly is one button whose `dialog.show()` will deadlock. R_swing_is_truth covers the *content* of the sync (field storage, `preventPeerEvents`, fire Swing event); R_callswing_envelope is the *thread envelope* around it. Re-entrancy: nested `callSwing` from inside an outer VT continuation runs inline (no nested VT spawn). Throws `IllegalStateException` if `UI.getCurrent()` is null — a missing UI at a peer→Swing seam is a programming error, not a soft incompleteness — **except during app shutdown** (a real tab close → termination; `EHelper.isShuttingDown()` is set by `JFrame.dispatchShutdownClosing` before the `WINDOW_CLOSING`-driven detach cascade): there the teardown-detach listeners funnel `removeNotify` through `callSwing` on the request-less tab-scope reaper thread with no current UI, which is expected teardown, not a programming error — so `callSwing` runs the callback **inline** (the browser tab is gone; nothing to push to) instead of throwing. See [D_shutdown_lifecycle](./emulators/decisions.md), D_callswing_funnel, D_callswing_loom.
9. <a id="R_vaadin_first"></a>**R_vaadin_first. Surrogates: Vaadin-first direct binding; API-only round-trip is not a goal.** `:surrogates` strives to reproduce the *UI functionality* of a Swing component fully — clicks fire ActionEvents, ButtonModel state drives ChangeListener fan-out, spinners step through values, sliders snap to ticks. It reproduces the Swing *API* only to the degree Vaadin has a semantic counterpart: a Swing setter writes to the appropriate Vaadin property directly, the matching getter reads that Vaadin property back. Minor round-trip loss is accepted and expected — `setText(null)` may read back as `""` (Vaadin's element text property can't represent null); `setBorder` → CSS → `getBorder()` reconstructs via `JComponentMixin.getBorder()`'s lossy CSS-parse per [SD_border_css_lossy](./surrogates/decisions.md#SD_border_css_lossy). When Vaadin has no counterpart for a Swing property, the default is `EHelper.onUnimplemented(self, "method", args)` + a javadoc line documenting the absence + **throw the value away** — **do not fabricate a `Store` shadow cache** just so a setter's value round-trips through its own getter. `Store` class carve-outs exist only when Vaadin has no equivalent concept *and* the Swing concept is materially used by migrated code: `NameStore` (Vaadin's `Component.id` is not the Swing `name` concept — different semantics, different DOM/CSS effects, and `name` powers cross-component lookup widely in migrated apps). A new `Store` requires the same kind of justification. R_vaadin_first pins the "fat surrogate" claim to UI functionality, not API completeness: SJSlider's orientation / inverted, SJSpinner's per-type inner peer, SJButton's ButtonModel-driven event fan-out are all in scope; fields that only exist so their own getter returns what the setter stored are not. Listener lists, `ButtonModel`, and installed `Action` instances drive UI behavior (event delivery, state machine, action dispatch) and so belong in the UI-functionality bucket — their storage is legitimate, not API round-trip. **User-Listener registration mirrors the same Vaadin-first rule.** When a Swing listener type has a Vaadin counterpart event source (`ClickNotifier`, `HasValue.ValueChangeListener`, `FocusNotifier` / `BlurNotifier`, `KeyNotifier`, …), the surrogate's `addXListener` subscribes to the Vaadin event and tracks the resulting `Registration` via the `Registrations` holder so `removeXListener` can tear it down. Two valid wiring shapes: per-registration (one Vaadin subscription per Swing listener) or shared (one Vaadin subscription drives a Swing-listener-list fan-out — SJButton's `ClickNotifier` → `ButtonModel` pulse → `EventListenerList` is this shape). Don't accumulate Swing listener lists without a Vaadin subscription behind them somewhere — that's storage for storage's sake, the listener analog of the shadow-cache anti-pattern. When Surrogate needs to plant a listener (e.g. to a model), it is OK to store the closure which removes the listeners, as a Vaadin `Registration`. **This stance is surrogate-only and is deliberately the inverse of [R_decline_effect_only](#R_decline_effect_only)**, which tells the *emulator* layer to keep the field and fire the event even when the effect is undeliverable; the asymmetry is the stage-2/stage-3 split of D_emulator_surrogate_split, not an inconsistency.
10. <a id="R_leaf_peer_lockdown"></a>**R_leaf_peer_lockdown. Leaf emulators lock down their peer.** When a JDK Swing class is a leaf in the *public* Swing hierarchy — no public class in `javax.swing.*` extends it, ignoring `javax.swing.plaf.*` since L&F is dropped per R_match_swing_errors sub-bucket (b) — the corresponding emulator omits the protected `(Component peer)` ctor, and its root public ctor calls `super(new SXxx())` directly, hard-coding the chosen Vaadin peer. Every instance — through any public ctor or any user-code subclass — peers over the chosen component; the type-system seam through which a subclass could swap peers is closed. The class itself stays non-final to match JDK shape per R_swing_is_truth: user-code subclassing for *behaviour* (composite JPanels, app-specific button wiring, custom JFrame entry points, …) inherits the locked peer and works fine; user-code subclassing for *custom rendering* (paintComponent override, pluggable BasicButtonUI) is already out of scope per R_match_swing_errors sub-bucket (b) and so doesn't constrain the lock-down. Non-leaf emulators (`JTextField` → `JPasswordField`, `JToggleButton` → `JCheckBox`, `JTextComponent` → `JTextField`/`JTextArea`, …) keep the protected `(Component peer)` ctor as the [D_peer_ctor_injection](./emulators/decisions.md#D_peer_ctor_injection) seam their subclasses pass their own peer through. Lock-down is independent per component — apply when the emulator's canonical peer is settled (typically once its surrogate has landed); a leaf without a surrogate yet may keep the protected ctor until the thin-down to avoid double-edits. **The framework may select among multiple canonical peer types for a given emulator based on framework-level configuration; user code cannot influence the choice.** (Today this carve-out applies to `JFrame` per [D_frame_strategy](./emulators/decisions.md#D_frame_strategy) — `@MainWindow` picks `SJPanel`, otherwise `SJFrame` — pinned at ctor time from annotation walk, not from anything user code passes.)
11. <a id="R_no_spi_selfregister"></a>**R_no_spi_selfregister. Library modules never self-register a `VaadinServiceInitListener` (nor `VaadinService`/session lifecycle listeners) via `META-INF/services` SPI.** `:emulators` and `:surrogates` ship such listeners as *classes* for the app to wire, but must not auto-register them — SPI-discovered `VaadinServiceInitListener`s **conflict with Spring's own bean-based discovery** when the migrated app runs on Spring, so a library that force-registers one breaks every Spring consumer. The **app** does the wiring: a plain Vaadin-Boot app adds the class to its *own* `META-INF/services/com.vaadin.flow.server.VaadinServiceInitListener`; a Spring app exposes it as a `@Bean`/`@Component`. Example: `vaadinx.swing.app.SwingBridgeEmulatorsBootstrap` (the single mandatory init listener — wires `BrowserTimeZone.fetch()` and `FocusTracker.install()` per UI *and* D_shutdown_lifecycle's tab-close detector → `AppTab.onTabClosed`) is registered by Sampler's SPI file and by each migrated app, never by `:emulators`. The rule is load-bearing, not defensive: converting `testapps/crud` to Spring Boot needed no change in `:emulators`, `:surrogates` or the then-vendored blocking-dialog module *because* none of them self-registers, and a bootstrap that is both in an SPI file and a bean runs every per-UI step twice, silently. **A third-party dependency is outside the rule, and one does it:** vaadin-uifiber-loom's `SessionLockCheck` (R_match_swing_errors case (9)) registers itself through `META-INF/services`. It is harmless in exactly the way the rule's worry is not — idempotent, so on Spring, where a `ServiceLoader`-found listener runs too, a second registration just checks twice ([D_blocking_dialogs_library](./emulators/decisions.md#D_blocking_dialogs_library)). (JDK SPIs like `java.util.prefs.PreferencesFactory` are unaffected — this rule is specifically about Vaadin service/session lifecycle listeners.) Tests may register such a listener on the *test* classpath (browserless, no Spring), guarding any browser-only wiring so it stays inert under Karibu unless a test opts in.

    **The exception: a module dedicated to one framework's plumbing may register itself, through that framework's own discovery.** `:emulators-spring` — whose entire reason to exist is making SB-Emulators work on Spring Boot — may ship a Spring auto-configuration that publishes the servlet registration and `SwingBridgeEmulatorsBootstrap` as beans, so a Spring migrator writes no host-app wiring at all. **This is not a hole in the rule; it is the rule's own rationale applied.** What the prohibition protects against is a *generic* module force-registering through `META-INF/services` and colliding with a framework's discovery in an app that never asked for it. A framework-dedicated module collides with nothing: it is **opt-in by coordinate** (you get it only by declaring it, so it cannot surprise a consumer who is not on that framework), and it registers through **that framework's own mechanism** rather than the SPI the conflict is about. Three limbs, all required:

    - **Dedicated means the module would have no reason to exist without that framework**, and nothing in it is usable off it. `:emulators-spring` qualifies. `:emulators`, `:surrogates` and every other general-purpose module do not, and no amount of framework-specific content inside one earns the exception — the answer there is a new dedicated module, which is the shape this exception exists to make possible.
    - **Register through the framework's idiom, never `META-INF/services`.** The Vaadin listener SPI file is precisely what conflicts with Spring's bean discovery, so shipping one *from* a Spring module would reintroduce the bug the rule names. A Spring module uses `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`.
    - **The registration stays conditional and overridable**, in that framework's own way — `@ConditionalOnMissingBean` for Spring. This is what keeps "the app does the wiring" true in substance: an app that declares its own bean still wins. An unconditional registration is the SPI's problem wearing a different hat, and is forbidden here too.

    The four-copies evidence and the `SessionInitListener`-vs-`createVaadinSession` measurement that makes the library servlet possible: [D_library_servlet](./emulators/decisions.md#D_library_servlet). The Spring module this exception exists for, why it was worth a module, and the Spring-version coupling it accepts are in the same entry.
12. <a id="R_no_vaadin_in_api"></a>**R_no_vaadin_in_api. Emulator public API never exposes a Vaadin type — the exception is by *provenance*, not by name or package.** Two limbs, both about the emulator's public surface being the JDK's:
    - **Types.** A method that shadows a JDK signature must be JDK-faithful: where the JDK says `java.awt.Component`, the emulator says `vaadinx.awt.Component` — never `com.vaadin.flow.component.Component`, **and never `java.awt.Component` either.** The rule has two halves and the second is the sharper one: a JDK type where the port exists makes the method *uncallable*, since after the import swap the migrator holds only the `vaadinx` type. Worse, an unsatisfiable signature teaches its own body to give up and then reads as a documented limitation — `JMenu.isMenuComponent` returned `false` unconditionally, `MenuElement.getComponent()` `null`, both correct given the signature and both wrong (D_r12_jdk_typed_half). A JDK type SB-Emulators does **not** port stays as it is (`javax.swing.KeyStroke`, `java.awt.Dialog.ModalExclusionType` — nothing to swap for), and reusing a JDK *interface* forces its types just as hard as extending a JDK class, so the violation there is in the reuse, not the method. A method on a **SB-Emulators-invented type with no JDK counterpart** is free to speak Vaadin — `EHelper`, `FormattedFieldStrategy.createPeer` (D_jformattedtextfield), `VaadinIconAdapter` — as is the peer accessor itself (`vaadinx.awt.Component.getPeer`, `Container.peerContentElement`), because no JDK class claims that name. The test is *"does the JDK define this signature?"* — not *"is it called `*Peer`"* (a naming convention goes stale silently) and not *"which package is it in"* (`getPeer` lives on the emulated `vaadinx.awt.Component`).
    - **Call hierarchy.** We emulate Swing's *call graph*, not only its API: a JDK hook the emulator exposes must actually be invoked by the internal path that invokes it in the JDK — **at least called, even if what it does is nothing.** An exposed-but-unreachable hook is worse than an absent one: a migrator's override compiles, looks wired, and silently never runs, which no compile error and no WARN inventory can catch.

    Rationale, the full API survey behind it, and the one violation it found (`JTable.prepareRenderer`, wrong on both limbs): [D_r12_provenance](./emulators/decisions.md#D_r12_provenance). Limb 1 is gated mechanically and allow-list-free by `emulators/src/test/java/vaadinx/R12ProvenanceTest.java`, one `@Test` per half; the JDK-typed half's 39 violations and the ported `vaadinx.swing.MenuElement` they forced are [D_r12_jdk_typed_half](./emulators/decisions.md#D_r12_jdk_typed_half).
13. <a id="R_decline_effect_only"></a>**R_decline_effect_only. Emulate the whole method; decline only the effect.** A Swing method decomposes into **state** (what it stores), **notification** (what it fires, and the fan-out that firing triggers), and **effect** (what the user ends up seeing). Incomplete emulation may drop the **effect only**. State and notification are pure Java — they cost nothing, need no Vaadin counterpart, and are what user code actually observes — so dropping them is the silently-wrong failure shape [R_no_vaadin_in_api](#R_no_vaadin_in_api) limb 2 exists to name: the migrator's listener compiles, looks wired, and never fires.

    **The JDK's method body is the specification, not a judgement about what seems reasonable.** Store the value where the JDK stores it and gate it where the JDK gates it — the two differ *within a single class*, so this cannot be reasoned out and has to be read: `java.awt.Window.setAlwaysOnTop` writes its field **before** the support check, so the JDK's own `isAlwaysOnTop()` echoes a request the platform never honoured, and echoing it is correct; `java.awt.Frame.setExtendedState` gates its write **behind** `isFrameStateSupported`, so `getExtendedState()` stays `NORMAL`, and staying `NORMAL` is equally correct. A blanket "keep the value" rule gets the second one wrong. Likewise the JDK often runs its fan-out **outside** the changed-or-supported guard — `setAlwaysOnTop` propagates to every owned window unconditionally — so "we can't honour this" never licenses skipping the fan-out.

    **Faithful notification means the JDK's notifications, exactly — no fewer and no more.** Firing an event real Swing never fires is the same class of bug as dropping one: a migrated app's `PropertyChangeListener` runs where it never ran on the desktop, and the migrator has no way to know SB-Emulators invented it.

    Exempt as ever: layout and painting (R_best_effort_behaviour / R_layouts_close_enough, R_match_swing_errors sub-bucket (b)) — neither maps onto the DOM and both are best-effort. **Emulator-scoped:** `:surrogates` keeps [R_vaadin_first](#R_vaadin_first)'s opposite stance (drop the value, no shadow `Store`) on purpose — a stage-2 migrator expects a Swing-app shape, a stage-3 migrator expects a Vaadin component, and per-view code never sees both ([D_emulator_surrogate_split](./emulators/decisions.md#D_emulator_surrogate_split)). The systematic audit that produced this rule — six fronts where SB-Emulators' Window/Frame/JFrame diverged from the JDK's own call graph — is recorded front-per-entry at [D_frame_state_pairs](./emulators/decisions.md#D_frame_state_pairs) / [D_window_fanout](./emulators/decisions.md#D_window_fanout) (this rule's worked example, `setAlwaysOnTop`) / [D_visibility_direction](./emulators/decisions.md#D_visibility_direction) / [D_window_displayable](./emulators/decisions.md#D_window_displayable) / [D_window_registry](./emulators/decisions.md#D_window_registry) / [D_rootpane_containment](./emulators/decisions.md#D_rootpane_containment) + [D_frameinit_shape](./emulators/decisions.md#D_frameinit_shape).
14. <a id="R_no_silent_improvements"></a>**R_no_silent_improvements. Reproduce Swing's contract exactly — never improve on it silently.** [R_best_effort_behaviour](#R_best_effort_behaviour) caps fidelity *downward* — we may fall short of Swing. This rule is the **upward** cap, and it is the one [R_decline_effect_only](#R_decline_effect_only) needs: "emulate the whole method" means up to Swing's behaviour, not past it. Where Swing's behaviour is documented or de-facto, reproduce it. Where Swing is buggy, surprising or undefined, reproduce *that* rather than quietly fixing it: a forgotten `revalidate()` still looks broken; an undefined dispatch order is not stabilised behind the migrator's back; a `null` argument Swing accepts-and-NPEs-later is not "improved" into an early throw. A kindness the migrator did not ask for is a debugging trap in two directions — the app works under SB-Emulators and breaks under real Swing (which still runs during a transitional period), or the migrator's code grows to depend on the fix and the migration gets harder to reason about and harder to reverse. Faithful reproduction keeps their mental model intact and keeps post-migration debugging symmetric with pre-migration debugging. **The paper cut is the point:** the migrator already learned it writing the Swing app, and reproducing it keeps that knowledge worth having. Carve-outs where browser reality forces divergence are [R_layouts_close_enough](#R_layouts_close_enough) and [R_infra_not_surface](#R_infra_not_surface) — those are about *capability*, not UX polish, and a capability gap WARNs via [R_match_swing_errors](#R_match_swing_errors) rather than being papered over. Rationale and the three rejected alternatives (auto-revalidate, a strict/lenient mode flag, per-case judgement at the API): [D_no_silent_improvements](./emulators/decisions.md#D_no_silent_improvements).
15. <a id="R_gpl_provenance"></a>**R_gpl_provenance. SB-Emulators' core is a derivative work of OpenJDK, licensed GPLv2 + Classpath Exception, and is not clean-room — and the licence follows the derivation *per module*, so establish the lane before writing a header.** The core's licence is the same as OpenJDK's because the *method* is reading OpenJDK's source as the specification. Full rationale and the rejected alternatives: [D_gplv2_ce_relicense](./emulators/decisions.md#D_gplv2_ce_relicense). **The lanes** — `:emulators` and `:emulators-printing` GPLv2+CE, `third-party/jcalendar-1.4` LGPL-2.1, the jgoodies fork, `testapps/inventory` and `testapps/jlawyer-shape` on upstream's terms, every other module **Apache-2.0**, and so are the docs, guides (bar the host-app seeds under `guides/1-swing-to-emulators/seed/`, **0BSD** because a migrator copies them into their own app), skills and build files, which is also the residual for any surface the map does not yet name — are [D_licence_lanes](./emulators/decisions.md#D_licence_lanes), mapped tree-by-tree in [PROVENANCE.md § Lanes](./PROVENANCE.md#lanes). The specification for everything below is **[PROVENANCE.md § Headers](./PROVENANCE.md#headers)**; `vaadinx.LicenseHeaderTest` is the gate.
    1. **Never describe the project, a module or a file as clean-room, independently implemented, or written without reference to the JDK** — and never attest that to anyone. Reading OpenJDK source is not a thing to be defensive about here: [R_swing_is_truth](#R_swing_is_truth) tells you to replicate the original behaviour, [R_decline_effect_only](#R_decline_effect_only) says the JDK's method body *is* the specification, and [R_infra_not_surface](#R_infra_not_surface) says outright to copy the code that calls the stub. A clean-room claim over that would be false, and 160 files named after a JDK class are the evidence.
    2. **Every `.java` file SB-Emulators authors starts with its lane's header, verbatim from PROVENANCE.md § Headers** — five texts, and the lane is decided by the *tree* before anything about the file is read. **`HDR_jdk_derived`** — the JDK counterpart's own Oracle notice byte-for-byte, then Vaadin's derived-and-modified block — when the class maps onto a JDK class *or* when any method body in it was ported from one. **`HDR_vaadin_gpl`** — Vaadin's GPLv2+CE notice with the Classpath exception inline — otherwise in the GPL lane. **`HDR_vaadin_apache`** — Vaadin's copyright plus Apache-2.0's own notice — on every Apache-lane tree (PROVENANCE.md § Lanes' Apache row — every module but the two emulator modules). **`HDR_vaadin_lgpl`** under `third-party/jcalendar-1.4` (rule 6 below). **`HDR_vaadin_0bsd`** under `guides/1-swing-to-emulators/seed/` — an unconditional grant, since those files become the migrator's own code. **Copy from a sibling file in the same module, never from another module** — that one habit gets the lane right for free. The Oracle block is **copied from that class's own source** (`$JAVA_HOME/lib/src.zip`, or the `jdk-25-ga` tag) and never edited, reflowed, templated or removed: its years differ per file, 42 distinct pairs across the 160 today, and its `DO NOT ALTER` line is an instruction we obey. The `:generator` emits `HDR_jdk_derived` itself, so a fresh emulator arrives correct.
    3. **Both directions are errors, and the false-attribution direction is the one that gets missed.** A missing Oracle notice breaks the retention term the licence rests on; an Oracle notice on a file Oracle did not write is a false statement — which is why PROVENANCE.md rejects JetBrains Runtime's shortcut of stamping "Oracle designates this particular file…" onto downstream code. Neither is the safe default, so when in doubt read the file and decide from what is *in* it: carried-over expression (a copied constant table, a translated body) earns `HDR_jdk_derived`; API shape alone — signatures, a listener interface's three methods — does not. **In the Apache lane that verdict is not a header choice at all**: the boundary a consumer sees is the jar, so JDK expression anywhere in the Apache lane is GPL code inside a permissive artifact, and the fix is to remove the expression — never to stamp the header, which `LicenseHeaderTest` rules 2 and 6 refuse from both sides. `JdkSimilarityTest` catches the expression itself — measured against `src.zip` on every build, so a body reproduced from memory fails too ([D_similarity_gate](./emulators/decisions.md#D_similarity_gate)); a failure there is fixed by rewriting against the javadoc, never by raising its limit.
    4. **A modified file's Vaadin year is its GPLv2 §2(a) date.** Editing a file in a year later than the end year of its `Copyright 2000-YYYY Vaadin Ltd.` line bumps `YYYY` (`HDR_jdk_derived`: the "modified by Vaadin Ltd in …" year too). The line is byte-identical to `vaadin/flow`'s in every lane, so the annual company-wide sweep is the same one-line change here as everywhere.
    5. **Never paste third-party code into an SB-Emulators file.** Linking is exactly what the Classpath Exception is for; copying Apache-2.0 / BSD / EPL / commercial text into a GPLv2 file is a different act, and a *dependency's* licence never authorises it. Vaadin-owned code (Flow, flow-components) is the exception — the copyright holder may relicense its own work — but say so in a comment. A whole upstream file goes to `third-party/` as its own module under its own licence, per the existing lane.
    6. **`third-party/` and `testapps/` are not relicensed and their headers are not touched** — including adding a Vaadin header to a file Vaadin did not write. `third-party/jgoodies-forms-1.2.1` (BSD fork), `testapps/inventory` and `testapps/jlawyer-shape` keep exactly what upstream gave them, files with no header included. `testapps/crud` is Vaadin-authored and follows the ordinary rule. **`third-party/jcalendar-1.4` is the third case and follows neither:** Vaadin-authored, so it carries Vaadin's copyright — but under **LGPL-2.1**, upstream JCalendar's licence, so its header is its own and `HDR_vaadin_gpl` on it is a build failure ([M1D_addon_upstream_licence](./migration/1-swing-to-emulators/decisions.md#M1D_addon_upstream_licence), gated by `LicenseHeaderTest` rule 5). Copy a header there from a sibling file in the same module, never from another module.
16. <a id="R_tolerate_off_ui_thread"></a>**R_tolerate_off_ui_thread. Component access off the UI thread is [R_match_swing_errors](#R_match_swing_errors) applied to one specific case: tolerate it, warn about it, help where it is cheap — and never invent a throw for the off-thread-ness itself.** Swing's documented policy is that *"all Swing components and related classes, unless otherwise documented, must be accessed on the event dispatching thread"* — but the JDK enforces nothing, so a desktop app can violate it for years with no symptom, and real Swing apps are full of it (`testapps/inventory` builds a validator's dialog inside `SwingWorker.doInBackground()`). A migrator cannot be asked to fix that as a precondition of running, so stage 2 copes. **We are not happy about it and we say so; we just refuse to make it fatal by itself.** Five limbs:
    - **R_match_swing_errors governs unchanged; off-thread-ness is not a new trigger.** Where Swing throws, throw what Swing throws — including when the thread context is *why* it throws, which the enumerated major-gap list already covers (case (1), `SwingWorker.get()` / `invokeAndWait` from the EDT, is exactly that — in the opposite direction, since it fires *on* the EDT). What is forbidden is adding *"you were off the UI thread"* as a further trigger: unlike the enumerated cases it is not a programming error with a one-line fix, it is the migrator's whole threading design, working on their desktop today. An emulator that throws for it alone refuses to run an app real Swing runs.
    - **Warn, once.** `vaadinx.EHelper.checkUIThread()`, reached through `vaadinx.awt.Component.getPeer()` and `withPeer()` — the only two ways from an emulator to its peer, which is why `Component.peer` is **private**: a new emulator method cannot forget a chokepoint it cannot bypass. One WARN per JVM with a diagnostic stack, deliberately **not** on `EHelper.warnHook` (that channel is the stub-WARN inventory the `WarnInventoryTest` gates assert on, and this is hygiene in *the migrator's* code, not an SB-Emulators gap). See [D_peer_access_chokepoint](./emulators/decisions.md#D_peer_access_chokepoint).
    - **Make it work where it is cheap.** A surrogate is touched only with the session locked and a UI current, so no call site needs reasoning about what Vaadin does inside it. Every emulator builds its peer **lazily**, once a UI is current, and every Swing→peer write goes through `vaadinx.awt.Component.withPeer(Consumer)` → `vaadinx.awt.PeerWriteQueue` ([D_lazy_peers](./emulators/decisions.md#D_lazy_peers)): **inline** when a UI is current; a **synchronous hop** onto the peer's UI when the peer is attached and that UI is open (gated over every setter by `vaadinx.OffUiThreadWriteTest`); otherwise **queued**, and drained in order at attach, at `getPeer()` with a UI current, or before the next write. That makes a worker that builds a form before showing it pay nothing per write, and the queue reorders nothing: it holds writes only while no UI exists to run them, which is not the `UI.access()` [D_sync_ui_hop](./emulators/decisions.md#D_sync_ui_hop) rejects for inventing an execution order Swing never had — [R_no_silent_improvements](#R_no_silent_improvements)'s territory ([D_peer_queue_shape](./emulators/decisions.md#D_peer_queue_shape)). Where the hop does run, it is synchronous because blocking can only reproduce a deadlock the app already has on the desktop (an EDT waiting on a worker that needs the EDT). A queued write must be a pure sink, and D_lazy_peers' ten rules for writing one are a checklist for every new or converted emulator; `vaadinx.LazyPeerTest` and the suite-wide `PeersOnUIThreadGate` fail the build on a peer built off the UI thread. **The one write that cannot wait is a window's visibility**, since a modal show parks right after it: it goes through `EHelper.runInUIThread`, which reaches the session's live UI through the thread's `EmulatorContext`. There a thread carrying **no context** throws (case (7) above, [D_no_context_throws](./emulators/decisions.md#D_no_context_throws)), because the migrator never wrapped where the work is started and a WARN at the write points at the wrong file; and where a context is present but no UI is reachable — a closed tab, a session going away — keep the state, drop the effect, WARN ([R_decline_effect_only](#R_decline_effect_only)). **The seam belongs on the emulator side of the emulator↔surrogate boundary** — the non-obvious part, because the code that actually needs the UI is usually in `:surrogates` (`Icons.imageIconToVaadinImage`'s `new Image(bytes, …)` resolves its URL against `UI.getCurrent()`), and fixing it there would be fixing it in the layer that by the next limb is entitled to assume a UI thread (bar that limb's model exception).
    - **Surrogates are Vaadin components and are held to Vaadin's rules.** By default, no checks, no hops, no defensive copies in `:surrogates`. **The exception is narrow: a surrogate may hop onto its UI thread, synchronously, only inside a callback from a Swing model** — a `TableModelListener`, a `DocumentListener`, a `ButtonModel`'s `ItemListener` — because a background thread mutating the model directly reaches the surrogate without passing any emulator method ([SD_background_model_hop](./surrogates/decisions.md#SD_background_model_hop)). **Never in a surrogate setter**: hopping a setter is the emulator's job, through `withPeer` ([D_attach_aware_hop](./emulators/decisions.md#D_attach_aware_hop)). Every `SHelper.runOnOwnerUI` call site carries `// Allowed by R_tolerate_off_ui_thread because callback from model: <the listener>` on the line above it, and `ModelCallbackHopMarkerTest` fails the build on one that does not. Otherwise a stage-3 migrator writing against `S*` classes owns their threading exactly as they would writing Vaadin directly, and stage 4 is the same. The asymmetry is [D_emulator_surrogate_split](./emulators/decisions.md#D_emulator_surrogate_split)'s, the same shape as [R_decline_effect_only](#R_decline_effect_only) vs [R_vaadin_first](#R_vaadin_first): **stage 2 protects you, stage 3 onward you are on your own, and per-view code never sees both.**
    - **Thread-unsafe in, thread-unsafe out — say this out loud rather than implying a guarantee.** An app that mutates components off the UI thread is thread-unsafe *as written*; emulating it makes it no more and no less so, and its outcome stays as unpredictable as its own unsafety. The hop is a promise about one thing only — that the peer push lands on the UI thread, serialised against the request thread. It is not a promise about the app's own races: the Swing-side field write happens *before* the hop, on the caller's thread, unsynchronised, so two threads mutating one emulator still race, as they would on the desktop. That is faithful ([R_no_silent_improvements](#R_no_silent_improvements): we do not invent safety Swing lacks) and it is the triage rule too — a misrender whose source is off-thread mutation is the app's race with new timing, not automatically an SB-Emulators bug. Reproduce it on the UI thread before believing otherwise.

    The mirror image is worth holding onto: **[R_callswing_envelope](#R_callswing_envelope) is the inbound envelope** (peer → Swing, a virtual thread so a modal dialog can park); **this rule's `withPeer` / `runInUIThread` is the outbound one** (Swing → peer, the UI thread so the write lands). Every peer write runs with a UI current, now or once one exists ([D_lazy_peers](./emulators/decisions.md#D_lazy_peers)), and a Swing model a worker mutates hops surrogate-side ([SD_background_model_hop](./surrogates/decisions.md#SD_background_model_hop)). Peer *reads* are not hopped but removed: a getter answers from emulator-owned state and never reads the peer ([D_emulator_owned_state](./emulators/decisions.md#D_emulator_owned_state)); what the queue left open about the seam is in [#34](https://github.com/vaadin/swingbridge-emulators/issues/34).

The map is exhaustive, and Apache-2.0 is also its residual, so a new top-level surface still gets a row of its own rather than being left to the net. Root [`LICENSE`](./LICENSE) is OpenJDK's own file verbatim (tag `jdk-25-ga`) and cannot be renamed or removed, since 160 byte-frozen Oracle headers name it by reference; [`LICENSE-APACHE-2.0`](./LICENSE-APACHE-2.0) sits beside it as a second root text, not a replacement. The agent-facing rule is [R_gpl_provenance](#R_gpl_provenance); the decisions are [D_gplv2_ce_relicense](./emulators/decisions.md#D_gplv2_ce_relicense) (why the core takes OpenJDK's terms) and [D_licence_lanes](./emulators/decisions.md#D_licence_lanes) (why the repository does not inherit them everywhere); the human-facing version is [DEVELOPING.md § Licensing](./DEVELOPING.md). A jar's `META-INF/` carries **its own lane's** licence text plus `PROVENANCE.md`, via the parent pom's `<resources>` block or the module's override of it.

A module answering no to both may be permissive whichever way its dependencies run, since linking in either direction is what the Classpath Exception permits — calling or subclassing the API is not derivation, or every migrated app extending `vaadinx.swing.JFrame` would be derived too. `:sampler` is the worked case: 433 `vaadinx` imports, 50 classes extending emulator types, and permissive. ## Current scope

**Sources of truth:** this section is the scope overview; decision rationale lives in the `D*` / `SD*` entries cited below (and in [emulators/decisions.md](./emulators/decisions.md) / [surrogates/decisions.md](./surrogates/decisions.md)), and design in the `architecture.md` docs.

**Sampler (validation testbed).** [`:sampler`](./sampler/description.md) is an internal Vaadin app that demos the Swing API rendered to Vaadin — exactly what `:emulators` is, made browser-runnable. Grows incrementally with `:emulators` scope; ships a small number of higher-level happy-path Karibu tests (one per route). Per-component coverage stays in `:emulators` and `:surrogates` test suites — Sampler is a validation gate, not a place to relitigate per-method behaviour. **Sampler is NOT a typical Swing app and NOT a support contract** (testbed scope ≠ commitment surface). Full role definition in [sampler/description.md](./sampler/description.md); to run it, see [sampler/README.md §"Run"](./sampler/README.md#run) (bare `./mvnw -C -pl sampler exec:exec` once the SB-Emulators modules are installed).

## Packages

- `vaadinx.awt` — AWT emulation of the `Component` / `Container` hierarchy.
- `vaadinx.awt.event` — AWT event classes and listeners that reference Component (`ComponentEvent`, `KeyEvent`, `MouseEvent`, `WindowEvent`, …). Fully ported — see D_event_port_policy.
- `vaadinx.swing` — Swing emulation of `JComponent` subclasses (`JFrame`, `JButton`, …).
- `vaadinx` — static helpers (`EHelper.onUnimplemented`, formatting).

**We port classes that sit in the Component hierarchy, the handful of interfaces that reference Component (`Icon`, `Border`, `LayoutManager`, `LayoutManager2`, `MenuElement`, `RootPaneContainer`), and every AWT event type that references Component (ported wholesale per D_event_port_policy).** An interface earns its port when reusing the JDK's would force JDK types onto an emulator's public surface — `MenuElement`'s `getComponent()` returns a `Component`, so reusing it left `JMenuItem.getComponent()` able to return only `null` ([D_r12_jdk_typed_half](./emulators/decisions.md#D_r12_jdk_typed_half)); `vaadinx.swing.MenuSelectionManager` is the WARN-stub that port drags in, since its own API traffics in `MenuElement`. Everything else — `Color`, `Font`, `Dimension`, `ActionEvent`, `ActionListener`, `Action`, models, `AWTEvent` itself — is reused unchanged from the JDK. See D_whitelist_porting for the class-porting rule, D_event_port_policy for the event-porting rule.

## Building

**Maven runs outside the sandbox, always.** `install` writes `~/.m2/repository`, which the sandbox
denies — the build dies on the parent pom with `Read-only file system` before a single module
compiles. Don't downgrade the command to fit the sandbox; disable the sandbox for it.

**Before anything that consumes SB-Emulators as artifacts — a migration round, a testapp build, an agent handed
a build command — rebuild the whole reactor clean:**

```
./mvnw -C clean install
```

Not `-pl … -am`, not incremental. The rebuild is cheap and bounded; recovering from a stale artifact
is neither, and it fails *misleadingly* — an agent reports a stumble against its own work rather than
"my toolchain was stale". Four stale modes, all observed: an IDE build poisons `target/` (Eclipse
compiles with JDT into the same directories Maven uses, and JDT rejects code javac accepts — see the
false positive `SJSpinner:476` documents, which surfaces as two `SJSpinnerTest` errors and a
`:surrogates` failure); `~/.m2` keeps yesterday's `third-party/` add-on jars, which are exactly
what a migration resolves by coordinate; and **a parallel session editing the same working tree**
leaves half-compiled classes behind — observed as a wave of `NoClassDefFoundError` in tests the
session never touched (`BorderLayoutTest`, `CheckboxTest`), cleared entirely by a clean rebuild;
and **a testapp's own `target/` outlives a change to its source** — the testapps are not reactor
modules, so until the root build learned to rebuild them in place, crud's stage-2 `target/classes`
kept a `META-INF/services` file from before its move to Spring Boot, registered
`SwingBridgeEmulatorsBootstrap` a second time beside the auto-configuration's bean, and every F5
logged a `TabScope` error that was chased as a library regression. **The tell for all four is the
same: failures in code you did not touch.** Rebuild before believing one.

**That one command also produces the kit** — the zip at `zip-distro/target/`, plus an unpacked copy
at `zip-distro/target/unzipped/swingbridge-emulators-<version>/` that exists for `KitLayoutIT` and
`KitSmokeIT` to read. **The kit for a migration round is neither of those:** `/build-kit` unzips the
artifact into a fresh temp folder **outside any git repository** and reports that as
`SWINGBRIDGE_HOME`, because a kit under `zip-distro/target/` is gitignored (and in Claude Code a
gitignored file has no LSP result locations — the artefact behind three rounds' "references are
dead" finding) and because a kit inside this repo lets the migrating agent walk up into the emulator
sources a customer would not have, per [M1D_lsp_recommended](./migration/1-swing-to-emulators/decisions.md#M1D_lsp_recommended).
"Rebuild first" and "have a kit to migrate from" are still the same step. **It also rebuilds every
testapp stage in place** — `clean verify` of `testapps/*/*/pom.xml`, bound to `:zip-distro`'s
`install` phase so the stages resolve what this same run just installed (a plain `verify` skips it;
`-Dtestapps.skip` skips it for one run, and the property's comment in `zip-distro/pom.xml` says why
the rebuild stays on by default).
`-Pkit` is a different build: it builds the *shipped* copies out of the unpacked kit, at the paths a
customer sees, which is what CI runs.

## Stub generator

Separate Maven module `:generator`. It reflects over a whitelisted JDK class and emits a `vaadinx.*` skeleton whose methods forward to `vaadinx.EHelper.onUnimplemented`. Run when expanding scope:

```
./mvnw -C -pl generator compile exec:java -Dexec.arguments="javax.swing.JButton,emulators/src/main/java"
```

The generator lives outside `:emulators` so it runs even when `:emulators` won't compile — the usual state when expanding scope. Generated output is a starting point, not the finished class.

## Doc conventions

The javadoc and doc conventions for this repo, the javadoc ones validated by a probe pass over `EHelper` / `JButton`:

- **Decision IDs are slugs, and you coin one rather than allocate it.** A new entry is named for what it decided (`D_surrogate_first`), never for "the next number" — kind prefix (`D_` emulators, `SD_` surrogates, `M1D_` migration, `R_` hard rule), 1–4 underscored words, no hyphens anywhere in the id. Numbering was abandoned because it **clashes across worktrees**: two branches each append the next `D94` and neither is wrong until they meet — it happened twice on `main`. A slug collides only when two branches actually decided the same thing, which is a conflict worth having. Every entry carries an explicit `<a id="…"></a>` immediately above its heading (sub-decisions get one inline, in their existing bullet shape), so link targets survive a heading reword. `DecisionIdTest` fails the build on a reference to an undefined slug, a slug defined twice, a dead link fragment, an old numeric ID coming back, or a `Q_` sub-question id cited from Java that no decision log mentions — the check that makes a slug's one weakness, being silently mistypeable, catchable. A forward reference to a slug no decision has earned yet belongs in a GitHub issue (§"Planning docs"), outside the check. Old numeric IDs translate at [DECISION-ID-MAP.md](./DECISION-ID-MAP.md), for commits and PRs written before the rename.
- **No history in javadoc.** A class or method doc states what the thing *is* and does today, never how it got there.
- **Decision-ID refs are rationale, not banned history — keep them; cut milestone narration.** `D*` / `SD*` / `R*` references (`per R_swing_is_truth`, `see D_callswing_loom`, `SD_sjbutton`) are pointers to *why*, and stay. But *completion-milestone framing* — "post-SD_sjbutton thin shell", "landed in the Nth pass", any "how it used to work" — is exactly what the no-history rule targets: state what the class **is**, not the milestone it arrived at. (This is the one line that keeps the no-history rule from colliding with the repo's heavy, legitimate `D*`/`SD*` cross-referencing.)
- **A `@param` / `@return` tag must carry something the signature cannot.** In Java the signature already carries the type, so `@param runnable the callback` merely restates `Runnable runnable`; add `@param` / `@return` only when they carry a nugget the signature can't: units, nullability, ownership ("new instance; receiver untouched"), or which of several overloads' contracts applies. A tag that only echoes the type is noise, same as a tautological summary sentence.
- **Doc-drift is mechanically checkable.** A javadoc block carrying `@param` / `@return` / `@throws` must sit on a method — if it drifts onto a field/constant (as `singleLiveUI`'s doc once had onto `ACTIVE_UI_KEY`), tooling binds it to the wrong symbol and the method reads as undocumented. After a large doc edit, sweep for the pattern: a `/** … @return/@throws … */` block whose next non-annotation declaration has no `(…)` before its `;`/`=`.
- **A doc under `guides/` may only link to what the distribution kit ships**, and the two placeholder tokens must be declared where they are used. `guides/` is migrator-facing and travels verbatim inside the kit at that same path, so a link out of it — to `CLAUDE.md`, a decision log, a module README, a testapp other than `crud` — is a dead link in the download *and* a persona leak in the repo. Fix by stating the rationale in place, or by an absolute `https://github.com/vaadin/swingbridge-emulators/blob/main/…` URL under an explicitly maintainer-facing "further reading" note. The two tokens are **`SWINGBRIDGE_HOME`** (the unzipped kit, or the repo root) and **`MIGRATED_APP_FOLDER`** (the app being ported): they appear in *commands*, never in links, and **every document that uses one repeats the Conventions block declaring it** — each doc is read standalone, and an undeclared placeholder is a dead link without the brackets. `GuideLinkScopeTest` (in `:emulators`, beside `DecisionIdTest`) gates both halves; `KitLayoutIT` re-checks resolution over the assembled kit. See [D_kit_link_scope](./emulators/decisions.md#D_kit_link_scope).
- **File-header `//` blocks (`// Hand-finished emulator…`) are maintainer notes, not doc-debt.** Many `vaadinx.swing.J*` emulators open with one, and it is often the *only* home of that class's architecture rationale (e.g. JToggleButton's D_jradiobutton peer-dispatch teaching, JMenuBar's tree-rebuild flow) — exactly the hand-finished WHY to preserve. Don't mass-delete on a doc sweep; cut one only when it merely duplicates the class javadoc. Moving (not deleting) such teaching into the `/**` class javadoc so API consumers see it is a per-file judgement call, never a sweep.

**`guides/`** — the **migrator-facing** docs tree, hand-authored from `migration/`'s maintainer-facing sources. `guides/1-swing-to-emulators/` is the stage-2 guide, ten references, the add-on index and the agent prompt. It sits at the repo root rather than under `migration/` because the persona split is the top-level fact about it and because the distribution kit ships it verbatim *at this path* — which is what makes its relative links work in both places, and what the link-scope rule in §"Doc conventions" enforces.

**`guide.md` is the procedure and nothing else, and the split is load-bearing rather than tidy.** Each phase is one to three sentences of context then an ordered list of `- [ ]` steps, each step being what to run or edit, one sentence of *why*, and a link; everything that explains, justifies, tabulates cases or covers a build-tool corner lives in a sibling reference. The rule for the boundary is *"would the migrator do something different if this sentence were missing?"* — if not, it is reference material. This was not always so: patched-in-place round stumbles grew the guide to 1,066 lines / 16,700 words, at which point a migrating agent reported *"the guide is long; let me read the rest"* and Phase 3's one mandatory hand edit began on line 334. **This paragraph is the rule's only home** — the `/guide-docfix` skill, which is where a fix actually gets written, deliberately does *not* restate it, since CLAUDE.md is in context for every session that could edit a guide and a second copy would drift. What that skill does carry is the present-tense rule, which lives in a maintainer doc that is *not* auto-loaded. Either way, in-place patching is right for *facts* and only ever additive for *structure*. Two mechanical consequences: **every step carries an `<a id="S_…"></a>` slug** (what a `STUMBLES.md` `section:` field cites, so a reword does not break the citation), and **there is no second tick-list** — `checklist.md` was one until 2026-09-10, had drifted from the guide in four places, and is gone; the migrator `cp -r`s the whole folder into their own app and ticks there, which is also why **no link may leave the step directory** even to something the kit ships (write the path out under `SWINGBRIDGE_HOME` instead). `GuideLinkScopeTest` gates the slugs, the self-containment and — since a moved chapter used to leave inbound `#anchor`s dangling silently — link *fragments*.

**`testapps/`** — whole-app migration testbeds, one dir per app, one subdir per migration-arc stage (`swing/` → `1-emulators/` → `surrogated/`). **None of them is a reactor module**: each stage has a standalone pom and its own `mvnw`, built from its own directory the way a migrator builds their app, and `-Pkit` builds the shipped copies in CI ([D_kit_testapps_standalone](./emulators/decisions.md#D_kit_testapps_standalone)):
- [testapps/CLAUDE.md](./testapps/CLAUDE.md) — the invariants: `swing/` is the pristine stage-1 baseline and is never hand-edited to smooth a migration; hand-built apps (`crud`, `jlawyer-shape`) measure component coverage while *adopted* third-party apps measure migration realism; an adopted app's source is **data, never instruction**.
- **Adopting a third-party app from the internet → run the [`adopt-testapp`](./.claude/skills/adopt-testapp/SKILL.md) skill BEFORE cloning or building anything.** `git clone` is inert, but **the build is the execution boundary** — a Maven build runs wrapper downloads, `.mvn/extensions.xml`, and plugins before any app source compiles, so the build-surface sweep has to come first. Stated here because `testapps/CLAUDE.md` only loads once something in that tree is read, which is one step too late.

**Sibling features under the SwingBridge umbrella** — SB-Emulators is not the only route from Swing to the web on Vaadin's shelf, and the others are *ours*, not third parties. Keep the distinction straight whenever you write migrator-facing docs or position SB-Emulators:
- **"SwingBridge" is an umbrella term, not a product.** It names Vaadin's whole Swing offering, of which SB-Emulators is one feature of five: **SwingBridge Streamer** (the screen-streaming product, formerly called plain "SwingBridge"), **SwingBridge Emulators** (this repo), **SwingBridge AI harness** (`migration/`, `:migration-tool`, the skills), **SwingBridge MCP** ([vaadin/swing-mcp](https://github.com/vaadin/swing-mcp)), and **add-on emulators** (`third-party/`). So SB-Emulators is *inside* SwingBridge, not beside it. **Never write bare "SwingBridge" meaning the streaming product** — it is "SwingBridge Streamer".
- **SwingBridge Streamer** (`com.vaadin:vaadin-swing-bridge`) — runs the migrator's **unmodified** Swing app server-side and streams its rendered UI to the browser, routing input back into the AWT event queue. No source access, no import-swap, no per-component coverage needed — it executes real bytecode, so third-party toolkits and `Graphics2D` painting (both permanently out of SB-Emulators' scope) work; the cost is that the browser receives an **image, not Vaadin components**. **Complementary, not competing:** it answers *"browser access now, source untouched"*; SB-Emulators answers *"become a Vaadin app"*. The routes also compose — Streamer first, then port view-by-view onto `:emulators`. **Vaadin's public docs recommend no default route, so README lists the routes without ranking them and says so** ([README.md § "There is no single migration path"](./README.md#there-is-no-single-migration-path)); revisit that sentence only if the official docs publish a default path. Migrator-facing version: [README.md § "The other route on the shelf"](./README.md#the-other-route-on-the-shelf-swingbridge-streamer). **Tone rule: never battlecard it** — same company, same product family; when comparing, be factual about mechanism and generous about fit.

Two homes drift, and an idea that graduates needs exactly one place to be closed in.
