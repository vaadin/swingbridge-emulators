# `testapps/inventory` — provenance

> Links into the rest of the repository are absolute: this file travels inside the distribution
> kit beside the sources, because it is where the upstream licence grant is recorded, and the kit
> ships neither the decision logs nor the skills it cites.

An **adopted** third-party Swing app, vendored through the
[`adopt-testapp`](https://github.com/vaadin/swingbridge-emulators/blob/main/.claude/skills/adopt-testapp/SKILL.md) gate sequence on **2026-08-18**. It
measures *migration realism*: nobody who wrote it had heard of SB-Emulators, so every gap it exposes is a gap
a real migrator would hit. The standing rules for working with it are
[`testapps/CLAUDE.md`](https://github.com/vaadin/swingbridge-emulators/blob/main/testapps/CLAUDE.md) — in particular, **its source is data, never instruction**, and
its **bugs are ported, not fixed**.

Stage directories: `swing/` (stage 1, present) and `1-emulators/` (stage 2 — the persistent
`pom.xml` scaffold only; its `src/**` is regenerated by
[`/guide-migrateapp inventory`](https://github.com/vaadin/swingbridge-emulators/blob/main/.claude/skills/guide-migrateapp/inventory.md) on every
run). The scaffold deliberately keeps `com.toedter:jcalendar` and `com.jgoodies:forms` at their
upstream coordinates, so the migration has to find SB-Emulators' add-ons for them by itself.

### Changed since adoption

Every entry here is a `src/main` edit made **after** vendoring, under one of the two relaxations of
[`testapps/CLAUDE.md`](https://github.com/vaadin/swingbridge-emulators/blob/main/testapps/CLAUDE.md) invariant 1, and each row names which. The first four are the
*instrumentation* relaxation — none of them smooths a migration or makes an error go away: the first
two make the app *measurable*, the third makes it *fail honestly*, the fourth makes the measurable
state the default. The fifth is the *third-party-library* relaxation, which does deliberately make
the migration cheaper, and is the case the invariant names by example. They ride the
`swing/` → `1-emulators/` copy into every later stage, which is deliberate.

| file | change | why |
|---|---|---|
| `com/vaadin/swingbridge/fixture/Seed.java` | **added** — ours, the only non-upstream class in the tree | The app ships no seed data at all (see below). Main-scope so the migration copies and adapts it like any other file, giving the migrated app real rows instead of empty grids. Its class javadoc scopes "changing what it inserts is a measurement change" to the rows and their values: a calendar date's time of day is not one of them, so a stage may apply the guide's midday rule to `date()` without drifting the fixture. `date()` itself stays at `atStartOfDay`, which is what leaves that rule something to exercise. |
| `com/ca/ui/Main.java` | one call, `Seed.seedIfEmpty()`, before `startApp()` | Makes the seed the app's own behaviour rather than a launcher's, so every stage seeds identically with no per-stage wiring. |
| `com/gt/db/SessionUtils.java` | the static initializer **re-throws** instead of printing and leaving `sessionFactory` null | Upstream turned any Hibernate misconfiguration into an unrelated NPE inside `getSession()`, arbitrarily far from the cause. Now it fails at class-load with the real stack trace. The rest of the file — including the two `HibernateException` swallows in `close`/`rollback` — is untouched; `BaseDAO` already re-throws. |
| `resources/hibernate.cfg.xml` | `connection.url` → `jdbc:h2:mem:inventory;DB_CLOSE_DELAY=-1` | Upstream's `./inventoryApp.db` had to persist because reference data was typed in by hand; the seed removes that need, so a throwaway database that comes up populated is the better default — and the default no longer depends on a test-scope resource shadowing the app's own config. Upstream's file-backed URL moved to `src/test/resources-filedb`, behind `-Pfile-db`. |
| `help.pdf` (project root) | **added** — a 542-byte valid one-page PDF reading "dummy help file" | Invariant 1's *dangling-asset* relaxation. Help → Read Manual shell-execs `cmd.exe /c start help.pdf` (`AppFrame:167`) and upstream never shipped the file, so the feature had no defined outcome for a migration to reproduce and an agent porting it would have to invent one. **Changes no stage-1 behaviour**: the baseline runs on Linux, where `cmd.exe` does not exist, so that menu item produced the catch block's error dialog before and produces it now — and `exec` resolves the name against the *process* working directory (`target/run/`), not the project root, so even on Windows this copy would not be the one it opened. Deliberately placed where the app's own code names it rather than on the classpath: relocating it onto the classpath and serving it as a download is the migration decision, and pre-placing it would answer that for the migrator. Being outside `src/`, it does not ride the `swing/src` → `1-emulators/src` copy — the agent has to notice it and move it. |
| `com/gt/uilib/components/input/DataComboBox.java` | the `AutoCompleteDecorator.decorate(this)` call and its import **deleted**, and `org.swinglabs:swingx:1.6.1` dropped from `swing/pom.xml` | The app's only SwingX call site, and the case invariant 1's third-party relaxation cites by name: dropping one decorator call beats emulating SwingX (huge, sprawling, partly abandoned — and forking it is explicitly rejected in [M1D_swap_vs_reimplement](https://github.com/vaadin/swingbridge-emulators/blob/main/migration/1-swing-to-emulators/decisions.md)). The combo loses type-to-filter; it is still a `JComboBox`, so the component surface the migration exercises is unchanged, and the two third-party Swing libraries that remain — JGoodies Forms and JCalendar — are exactly the two SB-Emulators ships an add-on for. **Deleted rather than inlined**: `AutoCompleteDecorator` installs a custom `Document` plus key listeners on the combo's editor, so vendoring it would have turned one deletion into migrating an autocomplete engine — more work than the dependency was, and past the relaxation's "no behavioural rewrite" test. |

**Changed, and not upstream's:** `swing/pom.xml`. It carries swingbridge-emulators-parent, the SB-Emulators artifactId, the four
publication skips, the fixture wiring and the `file-db` profile, plus the adoption's own two edits
(dead dependencies dropped, `maven-dependency-plugin` pinned to 3.11.0 — unpinned it resolved from
repository metadata at build time, F-9), and later the SwingX removal recorded in the table above. Upstream's `maven-compiler-plugin` block, which set
source/target 11, is **gone**: swingbridge-emulators-parent's `maven.compiler.release` overrides it anyway, so keeping
it would have been a pom that lies. Bytecode is therefore **major 65 (Java 21)**, not upstream's 55.
The sources compile clean at that level; if that ever stops being true, pin the module's own release
level and say so here.

## Trust

Scanned by a read-only subagent before any file was read by eye, then swept again during the
build-surface pass. **No prompt injection and no call-home was found.** All 132 non-`.git` files were
accounted for; 14 were read in full; the other 43 `.java` files are covered by pattern greps, not by
comprehension.

**Findings a reader of this app should know about:**

| # | finding | disposition |
|---|---|---|
| F-2 | `AppStarter` binds `ServerSocket` on **`0.0.0.0:45433`** (no `InetAddress`), and every accepted connection un-minimizes the window. Runs at every launch. | **accepted** — un-minimize is the only reachable effect, nothing is read from the socket. Live whenever the app runs outside a network sandbox. |
| F-3 | `Runtime.exec("cmd.exe /c start " + "help.pdf")` on Help → Read Manual; both operands compile-time literals, Windows-only, `help.pdf` absent. | **accepted** — reachable outcome is the catch block's error dialog. |
| F-4 | Hardcoded author back-door in `LoginUserServiceImpl:40-46`, checked **before** the database. | **accepted, and treated as a convenience** — but it **cannot fire**: the constants are MD5-length (32 chars) while `getSha256` emits 64. **Repairing the hash function would restore a live back door.** Must not be carried across a migration silently. |
| F-5 | `config.ini`: DES ciphertext, no reader in the tree, undecryptable with the in-source key. **96 bytes never read.** | **deleted.** If something breaks that this file might explain, it is the first suspect. |
| F-10 | `org.apache.log4j` used in 4 files, declared nowhere — arrives transitively via `jxl`. | accepted |
| F-11 | No `project.build.sourceEncoding` upstream; the build took the platform default. | accepted — swingbridge-emulators-parent now sets UTF-8. |
| F-12 | The built jar has `Main-Class` but no `Class-Path`, so **`java -jar` does not work**. | accepted — every documented launch uses an explicit `-cp`. |

**What was NOT checked** — as load-bearing as the findings:

- **Dependency behaviour is trusted by reputation, not audited.** Nothing was downloaded, unpacked,
  checksummed or signature-verified. log4j 1.2's network appenders sit on the classpath; the app's
  own `log4j.properties` declares only a `ConsoleAppender`, which is a statement about that file, not
  about the jar.
- **Greps do not find logic assembled to avoid the names** they search for.
- **Reflection is not exhaustively traced.** `AppFrame:93` does `Class.forName(...).newInstance()`
  over literals; Hibernate's own reflective proxying was not modelled.
- **PNG pixel data was never decoded** — type and `strings` only.
- Navigation is a **reflective panel swap**, not a `JTabbedPane` — a migration hazard, not a security
  one.

**Conclusion, at its actual strength:** reasonably safe for a local sandboxed testbed we intend to
read and migrate. **Not "audited", not "safe to deploy".**

## Fixture & run

**Credentials: `ADMIN` / `ADMIN`.** Created by `Main.addUserForFirstTime()` whenever no user exists —
which, on the in-memory default, is every launch.

The app ships **no seed data of any kind** (no `.sql`, no `import.sql`); upstream expects reference
tables to be typed in by hand via Entry → Initial Records before Item Entry works at all. The seed
automates exactly that, **through the app's own service layer** rather than SQL, so it exercises the
same insert path the UI uses instead of a parallel one.

- **Seed source:** [`swing/src/main/java/com/vaadin/swingbridge/fixture/Seed.java`](./swing/src/main/java/com/vaadin/swingbridge/fixture/Seed.java)
  — main scope, called by `Main.main` before the UI opens, skipped when the database already holds
  data, and it prints the row counts either way. Being an ordinary source file, it is *copied and
  migrated* with the app, so the migrated build comes up seeded too; it imports no `javax.swing`, so
  the swap itself leaves it alone — only its boot call site is a migration question.
- **Database config:** the app's own `swing/src/main/resources/hibernate.cfg.xml` points at
  `jdbc:h2:mem:inventory;DB_CLOSE_DELAY=-1` — in-memory is the default, no test-scope shadowing
  involved. The `DB_CLOSE_DELAY=-1` is load-bearing: without it H2 discards the database when the
  app's pool closes its last connection.

**Launch — seeded, in-memory, this is the default:**

```
cd swing
./mvnw -C test-compile exec:exec
```

`test-compile` buys nothing in this mode (there are no test sources, and the database config is a
main resource); it is in the command so the *same* command also works under `-Pfile-db`, which does
need its test resource copied.

Needs a display. The working directory is `target/run/`, because the app writes `./inventoryApp.db`
and `./log/` relative to wherever it starts.

**To drive it with an agent** ([swing-mcp](https://github.com/vaadin/swing-mcp) — an accessibility
tree plus interaction, and no source change needed), pass the agent through `exec.args`; `%classpath`
keeps the test-scope classpath the plugin computed:

```
cd swing
./mvnw -C exec:exec \
  -Dexec.args="-javaagent:/path/to/swing-mcp-agent.jar -classpath %classpath com.ca.ui.Main"
```

**File-backed H2 instead** — the only way to exercise `hbm2ddl.auto=update` against a *pre-existing*
schema, and anything that must survive a restart:

```
cd swing
./mvnw -C clean test-compile exec:exec -Pfile-db
```

The profile points `testResources` at [`swing/src/test/resources-filedb`](./swing/src/test/resources-filedb),
which holds upstream's own file-backed `hibernate.cfg.xml`; from `target/test-classes` it shadows the
main copy on the test-scope classpath and the app opens `./inventoryApp.db` in the working directory.

`clean` is not optional, and now it matters in the *other* direction: a stale
`target/test-classes/hibernate.cfg.xml` left by an earlier `-Pfile-db` build keeps shadowing after
the profile is gone, so a "default" launch would silently be on the file database. **Check the mode
in the log** — Hibernate prints `at URL [jdbc:h2:mem:inventory…]` or
`at URL [jdbc:h2:./inventoryApp.db…]` on every start. The seed skips itself when it finds data, so a
file database is seeded once and reused.

### What the seed puts in the database

Byte-identical on every launch, so a journey rubric can name ids and dates. **Every stage must seed
these same rows** — cross-stage comparison only means anything on identical data.

| table | rows | detail |
|---|---|---|
| Category | 3 | Laptops, Printers (returnable), Stationery (non-returnable) |
| Vendor | 3 | Acme Supplies, Globex Trading, Initech Hardware |
| UnitsString | 3 | pcs, box, kg |
| BranchOffice | 3 | Head Office, North Branch, South Depot |
| Item | 4 | ThinkPad T14, LaserJet 400, A4 Paper, ThinkPad T16 |
| Specification | 4 | cascaded from Item |
| Transfer | 4 | one per request number, one item each — see the state table below |
| ItemReturn | 3 | `RT-0001` + `RT-0002` against `TR-0001`, `RT-0003` against `TR-0004` |
| LoginUser | 0 at seed time | `ADMIN`/`ADMIN` is created immediately after, by the app |
| ApplicationLog | 0 at seed time | the app appends `Application Started` on every launch |
| CategorySpecifications | 0, permanently | orphan `@Entity` — nothing in the tree reads or writes it |

Reference tables get **three** rows each on purpose: a single-entry combo box looks identical whether
or not selection, ordering and value-binding actually work. `Transfer` and `ItemReturn` are seeded
because a manual happy-path pass leaves both empty, and they are two of the app's three `SwingWorker`
paths.

**The four transfers are four *states*, not four rows.** Which screen can see a `Transfer` is decided
by its state, and one row can only be in one, so each row buys a distinct one:

| request | item | qty | receiver | date | state | Return panel sees it? |
|---|---|---|---|---|---|---|
| `TR-0001` | 3 × ThinkPad T14 | 3 | Head Office | 2026-04-10 | partially returned, 1 outstanding (`RT-0001`, `RT-0002`) | **yes** |
| `TR-0002` | 3 × LaserJet 400 | 3 | North Branch | 2026-05-05 | outstanding, nothing returned | **yes** |
| `TR-0003` | 20 × A4 Paper | 20 | South Depot | 2026-06-01 | outstanding, but a non-returnable category | no — category filter |
| `TR-0004` | 1 × LaserJet 400 | 1 | Head Office | 2026-06-18 | returned in full (`RT-0003`), `STATUS_RETURNED_ALL` | no — `remainingQtyToReturn = 0` |

`RT-0002` returns its unit as **needs-repair**, which is the only seeded row taking
`saveReturnedItem`'s damaged branch — the one that builds a replacement `Item` and then never saves
it (upstream's, ported not fixed, and why the damaged return leaves `Item` at 4 rows).
Post-seed stock, after the transfers' decrements and the returns' add-backs: ThinkPad T14 **9** of 10,
LaserJet 400 **2** of 5, A4 Paper **80** of 100, ThinkPad T16 **3** of 3.

**Each transfer carries a cart of exactly one item, deliberately.** `TransferServiceImpl.saveTransfer`
calls `tx.commit()` *inside* its per-cart-entry loop, so a two-line cart commits the same
`Transaction` twice. That is upstream's bug to expose from a journey through the Transfer screen, not
something to bury a seeded row behind.

**Three tables stay empty, each for its own reason** — and the seed prints their counts anyway, so a
stage that grew rows in them gets noticed (unfiltered, because `ApplicationLog`'s own writer never
sets `dflag` and `DBUtils.readAll` only returns `dflag = 1`):

- **`LoginUser`** — `Main.addUserForFirstTime` creates `ADMIN`/`ADMIN` only when the table is
  **empty**. Seeding any user here would take the app's only known credentials away.
- **`ApplicationLog`** — the app writes a row on every launch and no screen reads the table; seeded
  history would be rows nothing consumes.
- **`CategorySpecifications`** — an orphan `@Entity`: no reader, no writer, so a row in it is
  invisible to every screen. The spec *labels* the entry form actually uses are `Category`'s own
  `specification1..3`, which are seeded.

The seed ends by running the Return panel's own query and printing what it returns
(`FIXTURE: Transfer rows the Return panel's search returns = 2`). Row counts prove insertion; that
line proves the rows survive the query's `remainingQtyToReturn > 0` / `dFlag == 1` /
returnable-category filters and are reachable by the only screen that consumes them — and that the
two rows built to fail those filters do fail them.

### Baseline behaviour — bugs included, because they are ported, not fixed

- **`Error:Can't read input file!` on every startup is upstream's bug.**
  `ResourceManager.getImage` feeds a `URL.toString()` into `ImageIO.read(new File(...))`, which
  cannot work, so it prints and returns `null` — meaning **a `null` image reaches Swing on every
  launch, and Swing tolerates it.** The emulators have to tolerate it too.
- **The Return panel's result table is starved to header height** at the app's default window size:
  the inner `JSplitPane`'s top region maxes out at 47px because the "Item Return Entry" cart panel
  below claims the rest. A search returning rows looks identical to one returning none. This is an
  R_layouts_close_enough *structural* layout target for the migration — not a cosmetic one.
- **Stock Query's search form stops well short of the right edge, and that is upstream's layout, not
  a migration defect.** `StockQueryPanel:358` adds the form to `BorderLayout.WEST`, which takes its
  *preferred* width and never the container's. Measured on a real JDK 25 with the app's own shape (a
  WEST panel of pref 969×293 plus a SOUTH button row): at a 1400px-wide frame the child is 969px with
  **431px of empty space to its right**, at 850px it is still 969px and therefore **clipped** — which
  is why the baseline screenshot cuts the `Reset` button off. The stage-2 build reproduces both
  numbers exactly (west track `968.8px`, gap `431px`, SOUTH row full width). The desktop hides the gap
  only because its window is narrower than the form; widen it and the same space appears. Filling it
  means `CENTER` instead of `WEST` in the app's own code — an app change, since SB-Emulators stretching WEST
  would be the divergence [R_no_silent_improvements](https://github.com/vaadin/swingbridge-emulators/blob/main/CLAUDE.md#R_no_silent_improvements) forbids.
  See [D_layout_west_keeps_pref](https://github.com/vaadin/swingbridge-emulators/blob/main/emulators/decisions.md#D_layout_west_keeps_pref).
- **The Return panel's request-number filter cannot work.**
  `TransferServiceImpl.notReturnedTransferItemQuery` restricts on a `requestNumber` property while
  `Transfer`'s field is `transferRequestNumber` — no such property exists, so a non-blank request
  number makes Hibernate throw instead of filtering. The seed passes `""`, which skips the
  restriction, so it never fires from the seed; it fires the moment a journey types into that field.
- **The `Save to Excel` chooser NPEs on cancel, on both grids.** `StockQueryPanel:138` and
  `ItemReturnPanel:326` discard `show*`'s return value and dereference `getSelectedFile()` on the
  next line, so a cancel (or the dialog's X, or ESC) — which nulls the selection, per the JDK's own
  `CancelSelectionAction` — throws. The throw lands *before* the `try` that would have shown
  "Could not save", so on the desktop it reaches the EDT's uncaught handler: stack trace on stderr,
  app alive, user told nothing. **The browser changes only its probability**, not its nature —
  cancelling an unexpected upload/name prompt is a routine thing to do, so a rare desktop crash
  becomes a common web one. Ported, not fixed, and *deliberately kept as a fidelity probe*: these
  two call sites are the ones the migration is *forced* to touch anyway (`showDialog` throws and is
  `@Deprecated`, [D_showdialog_throws](https://github.com/vaadin/swingbridge-emulators/blob/main/emulators/decisions.md#D_showdialog_throws)),
  which makes them the sharpest available test of whether a migrator edits *only* what the port
  requires. The expected port changes the direction and nothing else; reporting the NPE as a finding
  is fine, silently fixing it is the failure mode being measured.
- **`Validator`'s inline status-message path is dead code, by two independent upstream bugs.**
  All three `Validator` constructors take `Window parent` and **none of them assigns the field**, so
  `Validator.parent` is permanently `null`. Two consequences: `new JDialog(parent)` in `Task` and
  `createDialog(parent, "Error")` in `WarningDialog` get null owners, which Swing tolerates by two
  different routes — `JDialog(Window)` documents `null` as "no owner" and builds an ownerless dialog,
  while `JOptionPane.createDialog` substitutes `getRootFrame()`'s shared hidden frame — and
  `parent instanceof Verifier` is always false, so
  `validateFailed()` / `validatePassed()` never run and
  **`AbstractFunctionPanel:72`'s "Please enter data properly before saving" status message has never
  appeared, on the desktop either.** The second bug is why assigning the field would not revive it:
  every call site passes `mainApp`, and `AppFrame extends JFrame` — the only `Verifier` implementor
  in the app is `AbstractFunctionPanel`, a `JPanel`, which can never be the `Window` this field is
  typed to hold. So the path is unreachable by *type*, not merely by omission. Ported, not fixed:
  neither invariant-1 relaxation covers it — it is not the third-party-library case, and it is not
  the instrumentation case, since a one-line field assignment makes nothing observable (the type bug
  still holds) and there is no swallowed failure to make honest. The one counter-argument on record
  is that the validation path is un-smoke-testable in *every* stage while this stands; it loses to
  the fact that a baseline no longer matching upstream costs more than a status label does. The
  user-visible validation feedback that *does* work is unaffected — `Task.showPopup` still pinks the
  offending field, and the `isShowWarningDialog` `JOptionPane` still opens, both off paths that never
  touch `parent`. **Stated to the migrating agent** (see `.claude/skills/guide-migrateapp/inventory.md`),
  unlike the rest of this section.
- `string-resource.ini` does not exist; `ResourceManager.getString` falls back to
  `StrConstants.getMap()` by design.

### Verified journeys, and the ones still unexercised

Walked under swing-mcp from this module after vendoring: login as `ADMIN`/`ADMIN` → Stock Query →
Search returns exactly the four seeded items with their specifications, vendors and dates.

**Not exercised by the seed or by any walk so far:** Item Entry's save path, Transfer's save path,
`Save to Excel` on either grid, the `JDateChooser` popups, and Tools → Change UserName/Password. The
seed reaches the *data* those screens read; it does not prove their write paths.

## Testbed notes — what this app measures

Maintainer analysis, kept here rather than in [`README.md`](./README.md) because the README is
migrator-facing and inside a migrator agent's read scope: the dependency routing below is the
headline thing the round measures (does a migrator find `addons.md` unaided?), and the hazards
below are what it must discover from the code. The committed `1-emulators/` tree is derived, not
authored — regenerated on each `/guide-migrateapp inventory`; the committed one is run 1's
(2026-08-27), the first that boots, kept as the diff baseline for run 2.

### Why this app is here

The hand-built siblings measure **component coverage**; this one measures **scale, realness and
repeatability** ([`../CLAUDE.md`](https://github.com/vaadin/swingbridge-emulators/blob/main/testapps/CLAUDE.md) § "Two kinds of testapp").

| testapp | `.java` files | lines |
|---|---:|---:|
| `crud/swing` | 7 | 761 |
| `jlawyer-shape/swing` | 20 | 2,865 |
| **`inventory/swing`** | **65** | **10,130** |

3.5× jlawyer-shape — a genuine step up, still small enough that a full migration round is
affordable more than once. And it was written by a third party who has never heard of SB-Emulators, so a
round against it measures the migration rather than how well we predicted ourselves.

**What it does not buy: component breadth.** No `JTree`, no `JTabbedPane` (the README's "tabbed
interface" is a reflective panel swap over `AbstractFunctionPanel`, 12 subclasses — a migration
hazard, not a tab), no `JDesktopPane` / `JInternalFrame`, no clipboard, no drag-and-drop, no
printing. `jlawyer-shape` keeps the breadth crown. Expect this app to stress what already exists,
not to widen the surface.

The one place it goes deeper than either sibling: **~51 `JOptionPane` call sites**, the densest
stress of the riskiest machinery in the project (R_callswing_envelope /
[D_callswing_loom](https://github.com/vaadin/swingbridge-emulators/blob/main/emulators/decisions.md#D_callswing_loom) /
[D_joptionpane](https://github.com/vaadin/swingbridge-emulators/blob/main/emulators/decisions.md#D_joptionpane) modal parking on loom).

vanished** (JGoodies Looks and `jgoodies:binding` were in upstream's pom with zero and one usage
respectively and are gone; the 14 `setLookAndFeel` calls name the *JDK's* Windows L&F, not Looks).
This app's dependency list is what forced the add-on model into existence —
[M1D_addon_packaging](https://github.com/vaadin/swingbridge-emulators/blob/main/migration/1-swing-to-emulators/decisions.md#M1D_addon_packaging) /

`FormLayout` could not be waved through with
[M1D_custom_layoutmanager](https://github.com/vaadin/swingbridge-emulators/blob/main/migration/1-swing-to-emulators/decisions.md#M1D_custom_layoutmanager)'s
WARN-and-vertical-stack fallback: for 13 form-heavy panels "every form collapses into one column" is
the **structural** failure R_layouts_close_enough rules out of bounds, not the pixel last mile it
defers. Column-specs and row-specs are also the cleanest mapping onto `grid-template-columns` /
`-rows` any Swing layout offers, which makes it the first real proof of the
`CssEmittingLayoutManager` seam.

### Non-SB-Emulators hazards this app carries

Half the value of an adopted app is that it breaks in ways a hand-built testbed cannot.

- **`AppFrame`'s 13 statics** — including a `getInstance()` singleton, `static JMenuBar` /
  `JPanel bodyPanel` / `JPanel toolBarPanel`, and `public static boolean isLoggedIn` (which gates
  behaviour and flips in `handleLogin` / `handleLogOut`). UI components at application scope is the
  component prohibition verbatim: two users share one `bodyPanel`, so B's navigation replaces A's
  screen, and share one `isLoggedIn`, so **one login logs everybody in**. This is the first real
  test of [M1D_static_taxonomy](https://github.com/vaadin/swingbridge-emulators/blob/main/migration/1-swing-to-emulators/decisions.md#M1D_static_taxonomy)
  and it passed — run 1's sweep came out 13/13 against a golden verdict table written before the
  agent was spawned.
- **Hibernate is *not* the static hazard** it looks like. `SessionUtils.sessionFactory` is built once
  in a static initializer, which is correct — a `SessionFactory` is designed to be
  application-scoped and thread-safe. `Session` / `Transaction` are `BaseDAO` *instance* fields and
  every `DBUtils` static constructs a fresh one, so they are per-call in practice.
- **The DB layer's real defect is leaks, not races.** `find(Class, Long)` has no `finally`, so its
  session never closes; `runQuery(String)` touches `session` before `startOperation()`, so it NPEs
  or reuses the previous call's closed session; `findAll` has `// startOperation();` commented out.
  One desktop user leaking a few connections is invisible; on a server the leaks accumulate across
  every user until the pool is exhausted. Needs traffic to show.
- **`jxl` Excel export writes to a server-side `File`** chosen through a `JFileChooser` used to name
  an *output*. All three parts of that are decided —
  [D_showdialog_throws](https://github.com/vaadin/swingbridge-emulators/blob/main/emulators/decisions.md#D_showdialog_throws) (`showDialog` throws; the
  migrator supplies the direction), [D_save_binds_download](https://github.com/vaadin/swingbridge-emulators/blob/main/emulators/decisions.md#D_save_binds_download)
  (the download binds to the transfer *directory*), and
  [D_showsavedialog_return_ignored](https://github.com/vaadin/swingbridge-emulators/blob/main/emulators/decisions.md#D_showsavedialog_return_ignored)
  (the unchecked-return cancel NPE is upstream's bug, kept as a fidelity probe).
- **`Runtime.exec("cmd.exe /c start help.pdf")`** behind Help → Read Manual — UI intent, so it
  re-homes to a browser download. `help.pdf` sits at `swing/`'s project root, where the app's own
  code names it and *not* on the classpath: noticing the asset and relocating it is the migration
  decision.
- **`config.ini` read from the working directory** — CWD differs under a servlet container.
- **A single-instance `ServerSocket` guard** in `AppStarter`, deleted per
  [M1D_single_instance_guards](https://github.com/vaadin/swingbridge-emulators/blob/main/migration/1-swing-to-emulators/decisions.md#M1D_single_instance_guards):
  kept, it inverts into an outage, since the first session takes the port and every later session's
  probe succeeds and calls `System.exit(0)`.
