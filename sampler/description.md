# Sampler (`:sampler`)

`:sampler` is a Vaadin app that demos the Swing API rendered to Vaadin — exactly what `:emulators` is, made browser-runnable. A Vaadin-Boot app.

## What Sampler is

- **Demo of the import-swap drop-in.** Code reads as Swing (`vaadinx.swing.JButton`, `vaadinx.swing.JFrame`, …); runs as Vaadin in the browser. Per-route sub-views show one or more components configured to exercise the API.
- **Validation testbed.** Internal artifact for catching regressions in `:emulators` and `:surrogates`. Grows incrementally — only in-scope components appear; new components land here as their slice does.
- **Reproduction testbed.** When a migration target hits a bug, the minimal repro lives here as a route.

## What Sampler is NOT

- **Not an exhaustive test suite.** `:emulators` and `:surrogates` each ship their own component-level test suite — that's where method-level coverage lives. Sampler ships only a handful of higher-level happy-path Karibu tests (one per route) confirming the user path runs end-to-end with zero stub WARNs.
- **Not a browser test suite.** All Sampler tests are Karibu — server-side, synchronous, no headless browser, no Selenium, no real HTTP. The browser-runnable app is the demo affordance; testing stays in Karibu where it's deterministic and fast.
- **Not a support contract.** Components reach Sampler from `:emulators`, not the other way around. A component being demoed here doesn't promise typical-app migration coverage of every Swing nicety; the [intentionally-deferred classification](../CLAUDE.md) (R_match_swing_errors / D_gap_severity_triage) still applies per-component, calibrated against the CRUD baseline, not against Sampler's testbed scope.
- **Not a host-app template.** Sampler stays on Vaadin Boot whichever bootstrap the migration guides recommend. Nothing migrator-facing links into it, and switching would cost a Karibu re-plumb through `MockSpringServlet` for optics only. The Spring Boot lane's testbed is `testapps/crud`.
- **Not a typical Swing app.** Real migration targets are CRUD-shaped and JLawyer-shaped business apps. Sampler is breadth-first: one of every supported component, configured to exercise the API surface, not realistically composed into a working business workflow. Realistic-flow coverage lives in those real migration targets, not here.

## Scope

Sampler scopes to `:emulators` first and foremost — Sampler demos the Swing API as rendered to Vaadin, which is what `:emulators` is by definition. Surrogate coverage is transitive: most emulators delegate to a surrogate as peer (per [D_surrogate_first](../emulators/decisions.md#D_surrogate_first)), so exercising an emulator exercises its surrogate too.

**Pure-surrogate code paths** — `new SJSlider(...)` used standalone in a Vaadin app, not via `JSlider` — are NOT exercised by Sampler. Coverage for those paths lives in the `:surrogates` test suite (`SJSliderTest`, `SJSpinnerTest`, …). The architectural rationale for that split is in [surrogates/architecture.md](../surrogates/architecture.md) §"Handoff contract with `:emulators`".

## Structure

Single `@Route("")` `SamplerRoute` mounting an `@MainWindow` `SamplerFrame` (`vaadinx.swing.JFrame`) inline as the route content. Picking a demo swaps its `JPanel` into the content area via `removeAll() + add() + revalidate() + repaint()`.

`SamplerCatalogue.ALL` is the one declarative roster of demos — category, label, and panel factory per entry. Two nav components render it and neither hard-codes a demo:

- `SamplerNav` — the left column, a collapsible `JButton` group per category, at most one open at a time. Collapsing calls `setVisible(false)`, so a collapsed leaf is invisible to Karibu locators and a test must expand a category exactly as a user does.
- `SamplerJumpTo` — the north strip's flat `JComboBox` over every demo (`"Data › Tables"`), filterable by typing, for jumping straight to a known demo.

Both report the pick up to `SamplerFrame`, which swaps the content and pushes the selection into the *other* one so the two never disagree. **Adding a component slice is a new `*Panel` plus one line in `SamplerCatalogue.ALL`** — nav rendering and `NavigationSmokeTest` coverage both follow from it. Entry order matters: a category's entries must stay contiguous, since `SamplerNav` emits a category's header the first time it appears.

Current panels (in catalogue order):

- **Home** — `HomePanel`, landing page.

**Forms**

- **Form** — `FormPanel`, registration form (JLabel + JTextField + JPasswordField + JTextArea + JCheckBox + JToggleButton + FlowLayout/BorderLayout + setAction + InputMap/ActionMap + setBorder + setToolTipText + setInputVerifier + JRootPane.setDefaultButton).
- **Edit form** — `EditFormPanel`, CRUD edit-form host: blocking-modal `JDialog.setVisible(true)` parks its UI fiber until OK / Cancel disposes; the modeless variant returns immediately and the result flows back via a `WindowAdapter` on `DISPOSE_ON_CLOSE`.
- **Inputs** — `InputsPanel`, JSlider + JSpinner demo across all `SpinnerModel` variants (Integer / Long / Double / Date / List / custom) + cross-type `setModel`.
- **Formatted fields** — `FormattedFieldsPanel`, JFormattedTextField across formatter families (DateFormatter rendered as Vaadin DatePicker, NumberFormatter for Integer/Long/Double rendered as IntegerField/LongField/NumberField, MaskFormatter as TextField with browser `pattern` regex, DefaultFormatter / no-formatter fallback). One row per family with `setValue` / `getValue` round-trip and `commitEdit()` plus a focus-loss demo.
- **Dates** — `DatesPanel`, the date emulators (D_date_emulators): a `static final` `SimpleDateFormat` formats "now" and parses a typed string, and a `GregorianCalendar` runs `add(MONTH/YEAR)` field math with fields read back — all browser-zoned via `EmulatorContext.currentTimeZone()`.
- **ComboBoxes** — `ComboBoxesPanel`, JComboBox demo (non-editable selection + editable custom-value commit + custom DefaultListCellRenderer + a combo filled lazily in `popupMenuWillBecomeVisible`).
- **RadioButtons** — `RadioButtonsPanel`, JRadioButton in three shapes: standalone (no group, toggles like a checkbox), three-radio ButtonGroup with ItemListener-driven readout, and the D_abstractbutton_mixin_dispatch headline — mixed JCheckBox + JRadioButton in one ButtonGroup, proving the mixin-generalised mutex works across types.

**Buttons & actions**

- **Buttons** — `ButtonsPanel`, AbstractButton family (JButton + JCheckBox + JToggleButton).
- **ToolBars** — `ToolBarsPanel`, JToolBar (horizontal / vertical / margin) with button + `add(Action)` fan-out and both `addSeparator` overloads.
- **Menus** — `MenusPanel`, JMenuBar family (File / Edit / View / Help menubar + accelerators + JCheckBoxMenuItem toggle + JRadioButtonMenuItem chrome + nested submenu + separators).
- **PopupMenus** — `PopupMenusPanel`, JPopupMenu via `setComponentPopupMenu` (leaf items + nested submenu + top-level separators + JCheckBoxMenuItem).

**Data**

- **Tables** — `TablesPanel`, JTable demo (custom `AbstractTableModel` + `ListSelectionListener` selection bridge + `DefaultTableCellRenderer` subclass on the name column + `TableRowSorter` programmatic sort + regex `RowFilter` driven by a JTextField + `DocumentListener` + text/combo/checkbox cell editors).
- **Lists** — `ListsPanel`, JList demo (`DefaultListModel` mutation + single-selection `ListSelectionListener` + custom `DefaultListCellRenderer` + double-click-to-open via `locationToIndex`).
- **Trees** — `TreesPanel`, JTree demo (case-folder hierarchy over a `DefaultTreeModel` + single tree-selection via `addTreeSelectionListener` + right-click-to-select via `isPopupTrigger()` + `getRowForLocation` + custom `DefaultTreeCellRenderer` subclass distinguishing folders from documents + Add/Remove via `insertNodeInto`/`removeNodeFromParent` + drag-a-document-onto-a-folder re-parent via `TransferHandler` + `DropMode.ON` + rename-in-place via `startEditingAtPath`).

**Containers**

- **Layouts** — `LayoutsPanel`, the layout-manager family (FlowLayout / BorderLayout / BoxLayout / GridBagLayout weighted-column + REMAINDER / GridLayout / GroupLayout two-axis tree + Box struts/glue/rigid-area).
- **ScrollPanes** — `ScrollPanesPanel`, JScrollPane over all three content types (label stack / JTextArea / JTable) + the SD_sjscrollpane auto-scroll guard + JViewport / JScrollBar shadow-component surface.

- **Separators** — `SeparatorsPanel`, standalone JSeparator (horizontal between rows / vertical between regions / live orientation flip).

**Windows & dialogs**

- **Windows** — `WindowsPanel`, JWindow (centered splash with Timer-stepped progress + auto-dispose; toast anchored bottom-right via `Toolkit.getScreenSize()`).
- **Dialogs** — `DialogsPanel`, JFrame / Window family (lifecycle + WindowListener + defaultCloseOperation transitions + content-pane routing + glass-pane busy-curtain).
- **Option panes** — `OptionPanesPanel`, JOptionPane factories (showMessageDialog / showConfirmDialog / showInputDialog / showOptionDialog) parking through the JDialog modal-park machinery.
- **File dialogs** — `FileDialogsPanel`, `FileDialog` (LOAD / SAVE) + `JFileChooser` (open with extension filter / save), each parking the VT through the modal-park machinery then staging the browser upload.
- **ColorChoosers** — `ColorChoosersPanel`, JColorChooser in two shapes: embedded chooser with `ColorSelectionModel` + ChangeListener readout, and a blocking `showDialog` VT-park.
- **Desktop** — `DesktopPanel`, JDesktopPane + JInternalFrame (decorated non-modal overlay + drag/resize chrome + maximize / minimize-to-taskbar-chip / restore + vetoable properties).

**Text**

- **Caret** — `CaretPanel`, caret + selection (SD_caret_selection): server-side `select` / `setCaretPosition` /
  `replaceSelection` driving the browser's own caret, a `CaretListener` readout showing a caret the

  `NumberFormatDocument` uses.
- **EditorPanes** — `EditorPanesPanel`, JEditorPane in two shapes: a read-only HTML render (`setText` with `text/html`, then `setEditable(false)`), and an editable HTML editor whose current markup is echoed into a status `JLabel` by a `DocumentListener` (exercises the peer→Document R_swing_is_truth edit sync). - **HtmlViewer** — `HtmlViewerPanel`, the read-only HTML document viewer (about box / help viewer / report pane), which is what real code uses `javax.swing.text.html` for: an `HTMLEditorKit` carrying a stylesheet whose rules can be added live from a text field (D_htmleditorkit / SD_add_css_rule), a link-driven help browser where `HyperlinkEvent` activations drive `setPage` loads with a Back button and one page encoded in ISO-8859-1 (SD_hyperlink_listener / SD_setpage_audit), the editable gate showing links stop activating once the pane is editable, as in Swing, and the element model read back off the same rendered pane — `getElement(id)` / `getDefaultRootElement()` through the JDK-typed cast migrated code writes (D_htmldocument).

**Async**

- **Timers** — `TimersAndWorkersPanel`, Timer (start/stop ticking) + SwingWorker (publish/process/done + setProgress PCE).
- **ProgressBars** — `ProgressBarsPanel`, JProgressBar determinate (stringPainted + step/reset) and indeterminate (custom string) demos.

**Platform**

- **Focus** — `FocusPanel`, focus & traversal (D_focus_managers / SD_focus_tracker): a live focus-owner readout driven by AWT
  `FocusListener`s and reporting what `FocusManager.getCurrentManager()` answers, buttons that

- **Clipboard** — `ClipboardPanel`, `Toolkit` system clipboard round-trips (text / image / combined multi-flavor + empty-clipboard `UnsupportedFlavorException` probe) over `Transferable` / `DataFlavor`.
- **DnD** — `DragAndDropPanel`, `TransferHandler` drag-and-drop across JList / JTable / JPanel (source actions + createTransferable + canImport + importData + exportDone).
- **Preferences** — `PreferencesPanel`, `java.util.prefs.Preferences` (localStorage-backed) typed get/put/remove/flush over a user-node subtree.
- **Printing** — `PrintingPanel`, virtual PDF `PrinterJob` (getPrinterJob → setPrintable → printDialog → print of a two-page hand-drawn `Printable` → download dialog).

## Tests

Per panel: one `*WarnInventoryTest` that navigates to `SamplerRoute`, reaches the panel with the `Navigate.to("<label>")` test helper (which expands the panel's category, then clicks its leaf), drives the panel's user path, and asserts zero `EHelper.onUnimplemented` / `EHelper.onUnsupportedPeerShape` calls. Optionally an API-surface micro-driver per panel locking in zero-stub coverage on the slice's documented surface (the pattern `testapps/phase5`'s `WarnInventoryTest` established).

Plus a `NavigationSmokeTest` that walks every `SamplerCatalogue.ALL` entry and confirms each panel constructs without stub WARN, and a `NavHighlightTest` pinning that exactly one nav button carries the active mark whichever affordance moved it.

That's the bar for Sampler tests. Per-component method-level coverage stays in `:emulators` and `:surrogates`.

## Sampler's role

Sampler is the **load-bearing acceptance testbed**: every supported Swing component has a route + a `WarnInventoryTest`, and a green Sampler suite is the durable gate — the goal it enforces is "all supported Swing components, all major scenarios." It is a *validation* gate, not a *completion* target: Sampler running clean gives confidence to attempt the next migration target, but the project ships when real migration targets work, not when Sampler is "done." Sampler grows alongside `:emulators` — a component reaches a route as its slice lands.
