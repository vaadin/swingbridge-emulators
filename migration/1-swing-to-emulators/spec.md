# Spec — Swing to emulators

Internal working understanding of migration step 1: taking an existing Swing desktop app and getting it running as a Vaadin 25 web app via `:emulators`. Source material for the migrator-facing [`../../guides/1-swing-to-emulators/`](../../guides/1-swing-to-emulators) tree, whose [`guide.md`](../../guides/1-swing-to-emulators/guide.md) is the procedure and whose siblings are its references. Settled rules with rationale live in [`decisions.md`](./decisions.md); loose ideas and open design questions live in [GitHub issues](https://github.com/vaadin/swingbridge-emulators/issues) labelled `enhancement`, one issue per idea.

Cross-refs use bare prefixed IDs project-wide — see [`decisions.md`](./decisions.md) preamble.

## 1. What this stage is

The migrator starts with a running Swing desktop app and ends with the same app running in a browser, served by Vaadin 25. The work is **mostly mechanical** — rewrite `javax.swing.*` imports to `vaadinx.swing.*`, port `java.awt.event.*` event-class imports for events that touch Component, recompile against `:emulators`, run — with one mandatory non-mechanical refactor: splitting the existing `main()` into a process-level entry and a per-UI entry (see §3 step 3). Apps that use `System.exit`, static `JFrame` singletons, or custom `LayoutManager`s need additional refactors — see §7. Code shape stays Swing-shaped throughout: the migrator's `JFrame` is still a `JFrame` (an emulator one); their `ActionListener` still fires on button click; their `JTable` model still feeds rows; their styling iteration can begin in CSS without code changes.

The next stage (surrogate stage, view-by-view rewrite to `:surrogates`) is out of scope for this document. This stage's value prop is the cheapest path from "Swing desktop app" to "running web app" — mostly-mechanical rewrite, not weeks of redesign. See [CLAUDE.md §"Migration arc"](../../CLAUDE.md) for where this stage sits in the four-stage progression.

The foundational technique decision (import-swap, not binary drop-in) is M1D_import_swap. It implies: the migrator needs source access (or a recompilation path) for every Swing-touching dependency. Pre-rewritten forks of common third-party Swing libraries were that implication's open question and are now ruled: two ship as add-ons (M1D_addon_packaging, M1D_swap_vs_reimplement), both frozen as starter prototypes (M1D_addon_starter_status), and a library with no add-on falls into one of three states the guide enumerates ([`third-party-libraries.md` § "Libraries with no add-on"](../../guides/1-swing-to-emulators/third-party-libraries.md#libraries-with-no-add-on--the-three-states)).

**Scope: hard parts only; IDE cleanup is out of scope.** We assume the migrator has IDE access (or a Claude-assisted equivalent). Mechanical cleanup that an IDE handles well — unused-import pruning, dead-helper removal after a refactor, formatting — is **out of scope** for this stage's documentation. The migrator runs it as a separate cleaning round at their discretion. Implication for downstream docs: don't enumerate "now remove import X" steps in the guide; trust the IDE to handle it, and only call out cleanup when there's something the IDE can't see (e.g. a now-dead listener registration in a different file).

**`guides/` describes the current solution and nothing else; the history lives here.** A migrator-facing
doc states what SB-Emulators does today, in the present tense, with no trace of how it got there — no
"this used to throw", no "an earlier version of this guide said", no "the default changed", no
landed-in dates, no what-we-plan-next. The reason is not tidiness: **the migrator has no referent for
a past state.** They downloaded one version, they will migrate against that one version, and a
sentence comparing it to a version they never saw costs them reading and teaches them nothing — worse,
"now supported" and "no longer throws" read as *live* caveats about the release in their hands, so
history actively misinforms. The same goes for the guides' own revision history: a doc that argues with
its previous draft is a changelog wearing a reference's clothes.

**Where that material goes instead:** the durable *what* comes to this spec (edited in place, so it
always reads as the current understanding), and the *why*, including what a rule superseded and why the
old shape was wrong, goes to [`decisions.md`](./decisions.md) — which is built for exactly this, with
stable ids and fully-superseded entries shrinking to a pointer rather than being deleted. Both are
maintainer-facing, which is the point: the lesson is worth keeping, and its audience is whoever edits
the guides next, not the migrator reading them.

**This is a rule about the guides, not about the decision logs.** A `D_`/`SD_`/`M1D_` entry *should*
say what it replaced. And it is a rule the guide loop has to enforce rather than merely know, because
that loop is how history gets in: a round stumble is by nature a story about something that went
wrong, and the fix is the corrected present-tense statement, never the story. The
`/guide-docfix` skill carries the operational form of this and points back here; the sibling
step-vs-reference routing rule is not restated there, because its home
([CLAUDE.md §"`guide.md` is the procedure and nothing else"](../../CLAUDE.md)) is loaded into every
session that could edit a guide, and this one's home is not. [`testing.md`](./testing.md) is where the
loop itself is described.

## 2. Who this stage is NOT for

Apps built primarily on capabilities we've **permanently** dropped:

- **`JApplet`** — the JDK class itself was removed in Java 26 ([JEP 504](https://openjdk.org/jeps/504)); browsers dropped applet runtimes years ago. Nothing left to emulate.
- **Look-and-Feel dispatch** — `BasicButtonUI` / `MetalLookAndFeel` / `UIManager.setLookAndFeel`. Styling moves to a Vaadin+CSS pass, outside this project.
- **User-authored paint of *components* via `Graphics`** — `paintComponent(Graphics)`, custom-painted components, component-print (`JTable.print()`, `JTextComponent.print()`, `printAll`-based Printables). A speculative `Graphics2D`-to-SVG port is deferred indefinitely. Hand-crafted `Printable.print(Graphics)` — drawing shapes/text/images directly — is the carve-out: supported via the virtual PDF printer, see below.

Clipboard (`Transferable` / `DataFlavor`) and drag-and-drop are supported — clipboard via `vaadinx.awt.Toolkit`'s clipboard surface (D_clipboard), DnD via `vaadinx.swing.TransferHandler` (D_drag_and_drop). They import-swap rather than WARN-and-noop; the un-ported `java.awt.Toolkit` path throws `HeadlessException` at runtime.

`java.util.prefs.Preferences` is also supported ([D_preferences](../../emulators/decisions.md#D_preferences)) — with **zero code change**: `java.util.prefs` is not `javax.swing`, so there is no import to swap; SB-Emulators plugs in under the JDK `PreferencesFactory` SPI and backs the user tree with the browser's `localStorage`. Two caveats: the first pref read must run inside UI code (the same safe call sites as `BrowserTimeZone.get()` — see §7), and machine-wide `systemRoot()` is inert (writes WARN, reads return empty) since a per-browser store can't be shared across users.

Printing is also supported ([D_printing](../../emulators/decisions.md#D_printing)) — for the hand-crafted-`Printable` case: add the optional `:emulators-printing` dependency and swap **one** import (`java.awt.print.PrinterJob` → `vaadinx.awt.print.PrinterJob`; everything else in `java.awt.print` stays JDK). `print()` renders the pages server-side into a PDF and offers it in a download dialog — the user prints the PDF locally. Component-print sites (`JTable.print()`, `JTextComponent.print()`, `printAll`-based Printables) remain must-rewrite (server-side PDF report). See §7 for the server-print hazard on *unswapped* `java.awt.print` / `javax.print` code.

If the app's value is mostly in those surfaces, step 1 doesn't help yet — rewrite first or wait. Otherwise, in-scope features keep working; the dropped/deferred bits surface as WARN logs and the migrator triages.

## 3. The recipe

Concrete sequence the migrator runs to take an app from "Swing desktop" to "running on `:emulators`":

1. **Rewrite imports.** `javax.swing.*` → `vaadinx.swing.*`. `java.awt.Component` and `java.awt.Container` → `vaadinx.awt.*`. Component-touching event types (`java.awt.event.ComponentEvent`, `KeyEvent`, `MouseEvent`, `MouseWheelEvent`, `FocusEvent`, `WindowEvent`, `ContainerEvent`, `HierarchyEvent`, `InputMethodEvent`) → `vaadinx.awt.event.*`. Data types (`Color`, `Font`, `Dimension`, `Point`, `Rectangle`, `Insets`), event types whose source is `Object` (`ActionEvent`, `ChangeEvent`), action infrastructure (`Action`, `AbstractAction`, `ActionListener`), and models (`DefaultListModel`, `DefaultComboBoxModel`, `SpinnerNumberModel`, etc.) **stay JDK** — see M1D_import_rewrite_scope, M1D_event_port_policy. `instanceof` checks on the ported event types must rewrite too.

2. **Add `@MainWindow` + the route scaffold.** Annotate the app's main `JFrame` subclass with `@MainWindow`, then paste a one-class `@Route("") class AppRoute extends MainWindowRoute` whose `bootstrap()` calls `mainUI()`. The migrator owns the `@Route` (no auto-scan); `@MainWindow` is what lets the JFrame ctor find the bootstrapping route to render inline. Recommended `@PreserveOnRefresh` keeps the frame instance across browser refreshes.

3. **Split `main()`.** Existing `public static void main(String[] args)` divides into:
   - `main(String[])` — process-level entry (logging, config); runs once per JVM.
   - `mainUI()` — launch-level entry (constructs the frame, calls `setVisible(true)`); runs once per browser tab — not once per `UI`, since F5 builds a fresh `UI` while `@PreserveOnRefresh` keeps the route and its `bootstrap()` gate. No `args`: Vaadin's per-UI bootstrap has no JVM-args channel.
   - **Start-up work routes by owner, not by "process-level vs. UI-level".** The desktop conflated the deployment, the app launch and the user in one `main()`; the server separates them. Work owned by the **deployment** — schema / DDL, seeding, the first-run account, anything against the one shared database or filesystem — stays in `main()`, which is entirely pre-boot (`VaadinBoot.run()` blocks until the server stops, so no session, browser zone, `Preferences` or holder is reachable there). Work that recorded an **app launch** — an audit row, a per-launch counter — moves to `mainUI()`, which is once per browser tab: `MainWindowRoute.bootstrap()` runs at most once per route instance and `@PreserveOnRefresh` preserves it across F5, whereas a `UIInitListener` re-runs on every refresh and is never the home for the migrator's start-up work. The normative hook table (six hooks in run order, what each can reach) is [`../../guides/1-swing-to-emulators/lifecycle.md`](../../guides/1-swing-to-emulators/lifecycle.md).

   See [`emulators/architecture.md` §"Main window route"](../../emulators/architecture.md) for the full recipe.

4. **Wire the AppShell + servlet + SwingBridgeEmulatorsBootstrap.** Four pieces of one-time wiring — the first three are the modal-dialog enablement ([D_callswing_loom](../../emulators/decisions.md#D_callswing_loom)); the fourth registers the single SB-Emulators init listener:
   - `@Push` on the `AppShellConfigurator`.
   - A servlet extending `vaadinx.swing.app.SwingBridgeVaadinServlet`, which routes the session lock through `VirtualThreadAwareLock.wrap()` (per [D_vt_aware_session_lock](../../emulators/decisions.md#D_vt_aware_session_lock) and [D_library_servlet](../../emulators/decisions.md#D_library_servlet)). The subclass carries only the app's `@WebServlet` mapping. On Spring Boot the app writes no servlet at all: `:emulators-spring` auto-configures `SwingBridgeSpringServlet`, the `SpringServlet` twin, and its registration.
   - Chain `.useVirtualThreadsIfAvailable(false)` onto the `VaadinBoot` instance from step 6 (`new VaadinBoot().useVirtualThreadsIfAvailable(false).run()`).
   - Register `vaadinx.swing.app.SwingBridgeEmulatorsBootstrap` — one line in the app's own `META-INF/services/com.vaadin.flow.server.VaadinServiceInitListener` (on Spring Boot, `:emulators-spring` publishes it as a bean, so the app registers nothing). It wires the per-session browser time-zone cache (`BrowserTimeZone.fetch()` per UI-init, see [SD_browser_timezone](../../surrogates/decisions.md#SD_browser_timezone)), the focus-owner pointer's `focusin` bridge (`FocusTracker.install()` per UI-init, see [SD_focus_tracker](../../surrogates/decisions.md#SD_focus_tracker)), the emulator theme's default-fill rules ([D_theme_is_lookandfeel](../../emulators/decisions.md#D_theme_is_lookandfeel)), and D_shutdown_lifecycle tab-close detection. The library ships the class; the **app** registers it (R_no_spi_selfregister — never `:emulators` itself). There is no hand-rolled substitute: `MainWindowRoute` throws on attach when SwingBridgeEmulatorsBootstrap never ran for the UI, per M1D_bootstrap_canonical.

   All four are critical-path: skip any of the first three and modal dialogs deadlock silently; skip `SwingBridgeEmulatorsBootstrap` and the app throws at first load, at the route, naming the SPI file (M1D_bootstrap_canonical) — what it saves you from is `JSpinner(SpinnerDateModel)` / date-format `JFormattedTextField` throwing on construction (SD_browser_timezone), `FocusManager.getFocusOwner()` never seeing a focus change the browser made (SD_focus_tracker), unstyled emulator defaults ([D_theme_is_lookandfeel](../../emulators/decisions.md#D_theme_is_lookandfeel)), *and* the app never shutting down on tab close (D_shutdown_lifecycle). The Sampler app and `testapps/crud` carry the canonical wiring.

   Once step 4 is wired, hand-written `Date` ↔ `LocalDate` seams should use `BrowserDateUtils.toDate` / `BrowserDateUtils.toLocalDate` rather than `date.toInstant().atZone(BrowserTimeZone.get())` — the DatePicker peers convert with `java.util.TimeZone`'s arithmetic (SD_browser_timezone), which for pre-1900 dates differs from `java.time.ZoneId`'s by up to a day.

5. **JVM flag + JDK floor.** `--add-opens java.base/java.lang=ALL-UNNAMED` — required by the blocking-dialog machinery's virtual-thread runner (vaadin-blocking-dialogs). Add to dev/prod run configs and to test JVMs.

   **The runtime must also be JDK 24+.** Pre-[JEP 491](https://openjdk.org/jeps/491), `EHelper.callSwing`'s virtual thread pins its carrier — the Vaadin request thread holding the session lock — whenever any monitor sits above a modal call, so the response never flushes and the click that would unpark it never arrives: a deterministic deadlock, and the trigger lives in code SB-Emulators never sees (the migrator's own `synchronized` method, a JDK-owned lock). Bytecode stays at 21 for compile compat. `SwingBridgeEmulatorsBootstrap` refuses an older runtime at servlet init (R_match_swing_errors case (6)), which makes a wrong JDK a loud first-page-load failure; the **migrated app's own** `maven-enforcer-plugin` `requireJavaVersion [24,)` is what moves it to build time, and the guides carry that rule in the scaffold pom template. The full rationale, including why JDK 21 is a closed won't-implement, is in the root [`CLAUDE.md`](../../CLAUDE.md).

6. **Recompile + run.** The app's existing build invocation (e.g. `./mvnw verify` then run, or `./gradlew build && ./gradlew run` — whatever the migrator's setup looks like). The app boots into Vaadin Boot's embedded Jetty; visit `http://localhost:8080`.

The one *mandatory hand edit* in the migration is steps 2 and 3 (the `@MainWindow` annotation + `main()` split — non-trivial, requires thinking about the app's lifecycle). Steps 1, 4, 5 are mechanical or copy-paste; step 6 is the existing build invocation. Apps with `System.exit` calls, static `JFrame` singletons, or custom `LayoutManager`s need additional refactors — see §7.

## 4. What to expect at runtime

Two contracts the migrator sees, captured in M1D_runtime_contract:

**WARN logs** — every method we haven't implemented logs via `EHelper.onUnimplemented(className, method, args)` at WARN level (slf4j) and returns a sensible default (usually a no-op or a default instance). Read the WARN logs: each one is a method the migrator's app calls that `:emulators` hasn't built. Triage:
- Cosmetic (alignment flag, visual hint, Look-and-Feel touchpoint): ignore for now, file an issue if it materially affects appearance.
- Functional (a setter whose side effect the app depends on): file an issue, scope around it.
- Structural (a whole component category we haven't ported): wait for it to land or rewrite the affected view to a Vaadin equivalent early.

**Throws** — fire only on:
- *Inputs Swing itself rejects.* `getComponent(invalidIndex)` throws `ArrayIndexOutOfBoundsException`; `setValue(null)` on `SpinnerNumberModel` throws `IllegalArgumentException`; adding a component to its own ancestor throws `IllegalArgumentException`. Same exception type Swing throws — these are real bugs in the migrator's code that real Swing would have thrown on too.
- *Enumerated loom rescue cases.* `SwingWorker.get()` from the EDT, `SwingUtilities.invokeAndWait` from the EDT — each would have deadlocked under Swing too. Throwing surfaces the bug instead of hanging the request.
- *`EXIT_ON_CLOSE` close-attempt on a DialogStrategy `JFrame`.* Silent log-and-noop was rejected as hiding program-lifetime intent.
- *`BrowserDateUtils.toLocalDate` / `BrowserDateUtils.toDate` called before `BrowserTimeZone.fetch()` populated the session cache.* Used by `JSpinner(SpinnerDateModel)` and `JFormattedTextField` with a date formatter. Silent UTC fallback was rejected as producing dates an hour off in subtle ways while the migrator's wiring oversight is a one-line UI init listener fix. See [SD_browser_timezone](../../surrogates/decisions.md#SD_browser_timezone).
- *First `Preferences` read outside UI context.* Per [D_prefs_first_read_context](../../emulators/decisions.md#D_prefs_first_read_context), the first read warms a per-UI cache from the browser's `localStorage` and must run where a UI is current — inside `SwingUtilities.invokeLater` or an event listener. A read from a `static` initializer or `main()` before boot throws `IllegalStateException` with a pointer at the fix. Same safe-call-site rule as `BrowserTimeZone.get()` — no new migration rule; see §7.

The throw set is deliberately small and enumerated. Future cases land case-by-case — see M1D_runtime_contract, D_gap_severity_triage.

The import-rewrite mechanic in concrete terms — covered by M1D_import_rewrite_scope and M1D_event_port_policy:

**Headless HTML parsing needs no swap at all.** Code that uses `HTMLEditorKit` purely as a parser — a `ParserCallback` handed to the JDK's `ParserDelegator`, no pane anywhere — works whichever import it carries, because the nested `ParserCallback` / `Parser` types reached through *our* kit **are** the JDK's own types (inherited, not redeclared). That is what makes the two-class port above safe to state as a blanket rule rather than a carve-out, and it is pinned by `HTMLEditorKitJavaCompatTest` — the one Java test in `:emulators`, written in Java because the guarantee is a property of Java source resolution that Kotlin cannot express.

A regex `s/javax\.swing\./vaadinx.swing./` is too broad — it catches the constants holders and sub-package classes above. Narrow it to first-level `javax.swing.J*` plus a hand-picked list, or apply broadly and revert the carve-outs. The migrator's IDE optimize-imports pass after the swap should be a near no-op for the JDK side; everything that needed rewriting got rewritten in step 1 of the recipe.

**Underlying rule** (M1D_import_rewrite_scope): port what would silently fail server-side; leave what works unchanged on the JDK. Component-hierarchy classes have no AWT peer to render against; `EventQueue.invokeLater` posts to an AWT EventQueue thread that doesn't exist server-side (the runnable would queue and never run). Data types, models, and `Object`-source events don't depend on AWT runtime infrastructure and work untouched. The rule gives future "should we port X?" questions a principled criterion — e.g. `java.util.prefs.Preferences` read the *server's* preference store rather than each user's, exactly the silent-wrong-behaviour shape the rule flags; it has since landed per that criterion ([D_preferences](../../emulators/decisions.md#D_preferences) — `localStorage`-backed under the JDK `PreferencesFactory` SPI, so no import even needed swapping). (`Toolkit` also ported — D_toolkit_full_surface. Both examples are now historical; the criterion stands.)

`java.awt.EventQueue` ports as an application of this rule. The four static EDT methods (`isDispatchThread`, `invokeLater`, `invokeAndWait`, `getMostRecentEventTime`) carry working semantics — the first three delegate to `vaadinx.swing.SwingUtilities` and bottom out in `UI.getCurrent() != null` (the Vaadin UI-thread proxy); the fourth returns `System.currentTimeMillis()`. The remaining JDK surface (instance dispatch machinery, `postEvent`, `peekEvent`, `getCurrentEvent`, `dispatchEvent`, `push` / `pop`, `createSecondaryLoop`) is present so migrated code compiles, but each method WARNs via `EHelper.onUnimplemented` and returns a safe default — no AWT EventQueue dispatch thread exists server-side, so the dispatch contract can't be honoured (M1D_runtime_contract). Why ported despite not being Component-shaped: the JDK class would silently swallow `invokeLater(...)` calls server-side — exactly the failure mode the silent-failure rule rejects. The same shape applies to `vaadinx.swing.SwingUtilities`: EDT primitives + parent-walk helpers + Rectangle math are faithful; pixel / paint / accessibility / L&F surface WARN-stubs.

**Two sharp edges that no optimize-imports pass catches.** Both are scanned alongside §7's hazards — see §7's *Consolidated runnable form*.

- <a id="H_instanceof_ported_event"></a>**`instanceof` against a ported event type.** `event instanceof java.awt.event.ComponentEvent` returns `false` against a `vaadinx.awt.event.ComponentEvent`. *Detect:* grep `instanceof +([a-z0-9_.]*\.)?(ComponentEvent|KeyEvent|MouseEvent|…)\b` — or catch it at compile time by removing the `java.awt.event.*` imports first, which makes the compiler flag every reference.
- <a id="H_fq_awt_component"></a>**Fully-qualified `java.awt.Component` / `java.awt.Container` references inside code** (method signatures, casts, generic bounds). These aren't import statements, so optimize-imports won't touch them. *Detect:* grep `^(?!\s*import\s).*java\.awt\.(Component|Container)\b` — the leading-`import` exclusion is the point rather than tuning: an import line is Phase 2's tool's job, not a hand edit, and listing one under a section named for hand edits is what misleads.

## 7. Known migration hazards

Things that compile and "kind of run" but break in subtle migrator-visible ways. Each entry: what it is, how to detect, what to do.

**Local-LLM routing overlay.** Each hazard closes with an *LLM* tag per the [local-LLM migration target](https://github.com/vaadin/swingbridge-emulators/issues/21): *difficulty* — **mechanical** (any model, or a build-gate, handles it) / **judgment** (needs reasoning; escalate on the stuck-signal) / **likely-human** (expect to hand off) — × *sensitivity* — **secret-free** (customer may route this fragment to a cloud agent) / **sensitive** (on-prem only). **⚠silent** marks a hazard that fails with no compile-error / WARN / throw: it can't ride the stuck-signal, so it leans on a build-gate or a review instead. A held-loosely overlay — strip it if the target is abandoned; it doesn't touch the core detect/fix content.

**Consolidated runnable form.** `com.vaadin.swingbridge.migration.tool.hazardscan.HazardScan` — a second `main` in the same `:migration-tool` jar the guide's Phase 2 already runs, reached through the `bin/hazard-scan` launcher its distribution zip ships ([D_kit_tool_zip](../../emulators/decisions.md#D_kit_tool_zip)) — applies every `Detect:` pattern below, plus the two [§5](#5-what-gets-imported-where) import-rewrite sharp edges, in one pass over the tree and renders them as a grouped Markdown report:

```bash
bin/hazard-scan src/main/java --report swingbridge-migration/reports/hazards.md
```

It's a *finder* (always exits 0; false positives expected), not a gate; the two ⚠silent hazards keep their ArchUnit backstop. **The patterns are not duplicated here — they live in `META-INF/emul/hazards.tsv` inside that jar, and `HazardTableTest` joins the two by `H_` slug in both directions**, so a bullet whose `Detect:` names a grep with no row, or a row naming a bullet that no longer exists, reddens the build. That is what the anchors on the bullets below are for. Add-on jars can contribute rows to the same table, the way they contribute swap-table rows (M1D_addon_packaging); none does today. **What retires a "headless JDK class survives the swap" hazard is the class gaining a swap-table row, not the import-swap tool deleting the `java.awt.*` import** — deletion re-emits stay-JDK types verbatim, so an unported `java.awt.X` compiles and throws `HeadlessException` at first call, while a ported one cannot occur at all. `Toolkit` and `GraphicsEnvironment` both have rows ([D_graphics_environment](../../emulators/decisions.md#D_graphics_environment)), so neither gets a grep here: a scan for a hazard that cannot occur trains the migrator to ignore the scan.

**Static-state scope model (frames the "Static frame singletons" + "Multi-tab" hazards below).** A desktop app's `static` state is free (one JVM, one user); on the server every `static` field is shared across all users. The migrator routes each `static` to one of **three scopes** — **tab** (one running app instance; a [`FormerSingletons`](../../guides/1-swing-to-emulators/former-singletons.md) holder per [M1D_former_singletons](./decisions.md#M1D_former_singletons)), **session** (one user's private state), **application** (a `static` singleton, genuinely-global read-mostly infra) — via a decision tree whose **default is tab** (`static` meant JVM-global on the desktop, and the JVM's boundary is now the tab; application scope is the exception, argued from evidence that the state is global to *all users* and read-mostly), with a hard prohibition scoping **components** separately from data: a component is **prototype-scoped** (fresh instance each time) or **tab-scoped** (an instance field in the app's one component tree) — never `static`, never session, never UI-scoped. A `static` *accessor* over such state may stay static; only its body changes, so call sites are untouched — but that holds for **readers** only: a static method that *builds and assigns* a field routed to an instance field ("the tree is the storage") becomes an instance method too, since its new home is `this` and there is no scope left to resolve from. **`UI` scope is a trap, not a fourth option** — F5 destroys the `UI` and silently nukes anything hung off it. Full taxonomy + worked examples: [`../../guides/1-swing-to-emulators/static-fields.md`](../../guides/1-swing-to-emulators/static-fields.md); rationale + rejected alternatives (UI-scope, classloader isolation, the old two-pole rule): [M1D_static_taxonomy](./decisions.md#M1D_static_taxonomy). The taxonomy targets today's one-app-per-session reality (tab ≈ session); the application-scope verdicts re-open only if SB-Emulators relaxes to concurrent tabs ([multi-tab option 3](https://github.com/vaadin/swingbridge-emulators/issues/25)).

- <a id="H_system_exit"></a>**`System.exit(0)`.** One stray call kills the JVM and every other user's session. Compiles silently; runs catastrophically. *Detect:* grep `System\.exit` across the source tree. *Fix:* replace each call with `frame.dispose()` (close just this user's frame; on the `@MainWindow` JFrame with `EXIT_ON_CLOSE` set this also closes the session via the dispose hook — see [`emulators/architecture.md`](../../emulators/architecture.md)) or `UI.getCurrent().getSession().close()` (close the user's session directly). One shape is not a call-site fix at all: an exit in the `else` of a **single-instance guard** goes with the guard, which recipe step 3 deletes whole (condition, `else`, and the raise-the-window handler) — rewriting the call in isolation leaves an empty `else { }` in code that is about to be removed. Build-time enforcement shipped as a blanket direct-call ban, not a reachability gate — `MigrationGuardrails.checkJvmExit()`, see [M1D_guardrails_artifact](./decisions.md#M1D_guardrails_artifact). *LLM:* **mechanical · secret-free** — grep-complete, fixed substitution; the build-gate turns it into a compile-fail regardless of model.

- <a id="H_static_frame_singleton"></a>**Static frame singletons** (`MainFrame.getInstance()`, `App.frame`, `static final JFrame INSTANCE = new MainFrame()`). Swing apps stash the main frame in a static field and access it everywhere. Per M1D_single_ui_per_session, every session runs its own `mainUI()` while the `static` is JVM-wide — so the second user's start-up overwrites the first user's frame, and references from one user's listeners point at another user's frame. (A second tab in the *same* session is curtained, not run, so the leak is cross-user, not cross-tab.) *Detect:* grep `static .*JFrame` and `getInstance()` patterns. *Fix:* resolve the frame at use-time via `UI.getCurrent()` (or the active-UI pointer the `@MainWindow` route maintains). **A Vaadin component must never be cached in a `static` field *or* a session attribute** — a component belongs to a UI, not a session; session-stashing it couples the app to the one-active-tab model and reintroduces the session-scoped-view failure under multi-tab. See [session-scoped route](https://mvysny.github.io/session-scoped-route/). *LLM:* **judgment · secret-free · ⚠silent** — part of the static sweep: a mis-scoped component compiles, boots, and passes the WARN inventory, then leaks cross-user. Detection is the mechanical `Q_component` ArchUnit lint (component-in-static/session); the use-site rewiring is judgment. Silent → **review-gate, not stuck-signal**. `Q_component` of the static-state scope model above — full tree + examples in [`static-fields.md`](../../guides/1-swing-to-emulators/static-fields.md), rationale in [M1D_static_taxonomy](./decisions.md#M1D_static_taxonomy).

- <a id="H_custom_layoutmanager"></a>**Custom `LayoutManager`.** A migrator's hand-rolled pixel layout can't be translated (no synchronous child measurement server-side): it renders as a **vertical stack with a WARN** (M1D_custom_layoutmanager). *Detect:* grep `implements LayoutManager` / `implements LayoutManager2`. *Fix:* rewrite to a built-in (`FlowLayout`, `BorderLayout`, …) or implement `vaadinx.awt.CssEmittingLayoutManager` to map the layout's intent to CSS — see [`decisions.md` M1D_custom_layoutmanager](./decisions.md#M1D_custom_layoutmanager). *LLM:* **judgment · secret-free → cloud-OK** — the marquee cloud-routable island: mapping a layout's intent to CSS is creative work, but the code is generic UI plumbing ("put these boxes here"), not business rules, so the customer may hand this fragment to a cloud agent without breaching the privacy premise.

- <a id="H_modal_from_listener"></a>**Modal dialogs called from listeners** (`button.addActionListener(e -> JOptionPane.showMessageDialog(this, ...))`). Works correctly *only if* the production wiring (recipe step 4) is in place. Without the AppShell `@Push` and the servlet's `VirtualThreadAwareLock` routing, the dialog's blocking `show()` never renders — and without the lock routing each session's first request already fails, naming the fix. *Detect:* check that recipe step 4 is wired before any user-facing modal flow. *LLM:* **mechanical · secret-free** — a one-time recipe-step-4 wiring precondition (either wired or not), not a per-call-site edit.
- <a id="H_modal_under_monitor"></a>**A modal dialog shown inside `synchronized`, while another listener enters the same monitor.** On the desktop every listener runs on the one EDT, which re-enters a monitor it already holds, so a `JOptionPane` shown from a `synchronized` method never blocks the next listener. Under SB-Emulators each listener is its own UI fiber, a thread of its own: the second one — the dialog's own button handler, a `Timer`, another tab's request — waits for the monitor *while holding the session lock*, so the first one's answer can never be processed, and the session freezes for good. The lock-hold watchdog WARNs with the waiting listener's stack after 10 s ([D_blocking_dialogs_library](../../emulators/decisions.md#D_blocking_dialogs_library)). *Detect:* grep `\bsynchronized\b`, then for each hit ask whether the guarded code, or anything it calls, opens a modal dialog, and whether any other listener or `Timer` enters the same monitor. *Fix:* decide under the lock, ask outside it — move the modal out of the `synchronized` region. *LLM:* **judgment · secret-free** — which monitors a modal can sit under is a call-graph question, and most hits guard no dialog at all.

- <a id="H_timezone_drift"></a>**Date/time zone drift.** Swing runs in the user's local JVM zone; the server runs in its own while users sit in arbitrary browser zones, so field-form conversions (format / parse / `now()`) drift — `1815-12-10` renders as `1815-12-09` a zone west of the server, invisible when the dev machine shares the server's zone. **`SimpleDateFormat`, `Calendar`, and `GregorianCalendar` are now import-swap emulators** (`vaadinx.text.SimpleDateFormat`, `vaadinx.util.Calendar` / `vaadinx.util.GregorianCalendar` — [D_date_emulators](../../emulators/decisions.md#D_date_emulators)) that default to the browser zone, so the common `fmt.format(date)` / `cal.set(y,m,d); cal.getTime()` idioms are fixed by the swap alone — no rewrite. **`java.time` is *not* emulated**: `LocalDate.now()`, `DateTimeFormatter.ofPattern(...)` (no `.withZone`), `ZoneId.systemDefault()` still read the *server* zone; pass `BrowserTimeZone.get()` as the `ZoneId` by hand. Class-load timing: a `static final SimpleDateFormat` field is safe (the emulator's construction is session-free), but a raw `BrowserTimeZone.get()` — or a `DateTimeFormatter` built from it — in a `static {}` block / `static final` field / `main()` still throws `IllegalStateException` (SD_browser_timezone); defer it to a UI-thread call site. The inverse shape — code reached *only* from `main()` or pre-boot (seeding, schema setup, a first-run bootstrap) — has no browser zone to defer to, because no user exists there, and per [M1D_pre_boot_server_zone](./decisions.md#M1D_pre_boot_server_zone) it **keeps the server zone** rather than naming one: no browser exists to disagree with it, and the intranet deployment these apps sit in makes the server's zone its users'. Two consequences. **Bucket-1 emulator code reached from `main()` does not throw** — with no session and no `EmulatorContext` it takes the same path as a background thread, WARNs once, and formats in the server zone; so "change nothing" holds for pre-boot code, and it is deliberately *not* tagged `// TODO[browser-tz]:` (the fix would land in a shared date utility called from both sides — a refactor bought for no gain, where bucket 3's same decision costs one argument at the seam). **`java.time` calendar dates still move to midday**, the one part not left to fix-when-it-bites, because that value is *stored*: a zone is a one-line change later, midnight-stored rows are a data migration. *Detect:* grep `\b(SimpleDateFormat|Calendar|GregorianCalendar)\b` (bucket 1 — found so it can be checked off, since the swap alone fixes it) and `DateTimeFormatter\.ofPattern|\.(now)\(\)|ZoneId\.systemDefault|TimeZone\.getDefault` (bucket 3 — the `java.time` residual that needs the hand fix). Bucket 2 (date code on background threads) and the shared-`Calendar` anti-pattern have their own entries below. *Fix:* the per-bucket recipe is in the guide's ["Date and time handling"](../../guides/1-swing-to-emulators/guide.md) chapter. *LLM:* **mechanical / judgment · secret-free** — the `SimpleDateFormat` / `Calendar` swap is mechanical (import-swap alone fixes it); the `java.time` residual (pass `BrowserTimeZone.get()` as the `ZoneId` by hand) is judgment — the model must recognize which zone applies and where.

- <a id="H_showdialog_direction"></a>**`JFileChooser.showDialog` — no direction declared, and the browser needs one.** On the desktop no `show*` variant reads or writes a byte: all three put up a picker, return a `File`, and the app does the I/O — so `showDialog`'s `CUSTOM_DIALOG` costs nothing and the JDK never acts on it. In a browser LOAD and SAVE are different machinery ([D_file_load_path](../../emulators/decisions.md#D_file_load_path) upload vs D_file_save_two_dialog name-prompt + download link) that must be committed *before* the dialog opens, and `CUSTOM_DIALOG` names neither. Guessing LOAD — the literal JDK reading — silently breaks the common idiom of naming an *output* with a custom-button chooser: the user gets an upload prompt, the app writes a fine file server-side, no download is ever attached, and the export **reports success**. So per [D_showdialog_throws](../../emulators/decisions.md#D_showdialog_throws) it throws `IllegalStateException` (R_match_swing_errors throw-trigger case (4)) and carries `@Deprecated`. *Detect:* grep `\.showDialog\s*\(` — and the compiler, which names every call site whether or not anyone walks it (a `JColorChooser.showDialog` hit is a false positive; that one is fine). *Fix:* read what the surrounding code does with `getSelectedFile()` — **reads** it → `showOpenDialog(parent)`, **writes** it → `showSaveDialog(parent)`; to keep the custom label, `setDialogType(...)` with the matching type, then `setApproveButtonText("…")`, then the show call — the JDK's `setDialogType` resets the label on a type change, and a fresh chooser is `OPEN_DIALOG`, so a label set before `showSaveDialog` alone is lost; a runtime-conditional direction branches and calls the matching variant per branch. Can't tell? Leave the call and mark it TODO — it neither compiles clean nor runs, so no silent wrong behaviour is reachable. Two things belong at the same call sites, and only one of them is a fix. **The unchecked return value is ported as-is, not fixed**: most callers ignore it, so cancel nulls the selection and the next line NPEs — but that is the app's pre-existing bug (desktop Swing nulls the selection on cancel too, via `CancelSelectionAction`) and the emulator reproduces it faithfully on both paths. What the browser changes is the *hit rate* (cancelling an unexpected upload widget is routine where cancelling a deliberately-opened desktop save dialog was not) and the *symptom* (the NPE escapes the listener into Vaadin's `ErrorHandler` — logged, no dialog, button looks inert — and the app's own `catch` around the write never fires, since the throw precedes the `try`). The guide states the behaviour, tells the migrator to record it and fix it in a **separate** commit after the port verifies, and gives the guarded form for that commit — because this is a call site the port is *forced* to touch, so mixing an unrelated behaviour change into the required edit is exactly what makes a migration diff unreviewable. The inventory testapp keeps its two NPEs on purpose for the same reason, as a fidelity probe (`testapps/inventory/PROVENANCE.md`). The second, which *is* a note rather than a fix: **deriving a path from the name is fine** — the download watches the target's *directory* ([D_save_binds_download](../../emulators/decisions.md#D_save_binds_download)), so `+ ".xls"` and multi-file saves are offered under the names the app actually produced; only a write to an unrelated absolute path is unreachable, and that logs a WARN when the user closes the dialog empty-handed. Full triage prose: the guide's ["Runtime contract"](../../guides/1-swing-to-emulators/guide.md) chapter. *LLM:* **judgment · secret-free** — detection is grep-complete *and* a compile warning *and* a throw, so this rides the stuck-signal rather than needing a review-gate; the resolution is a bounded local read ("does the next statement read or write this path?"), and an unresolvable site has a fail-loud default rather than a silent one. This is the fenced shape the target wants: judgment that cannot fail quietly.

- <a id="H_preferences_read"></a>**`Preferences` reads from class-load-time initialisers or `main()`.** Per [D_prefs_first_read_context](../../emulators/decisions.md#D_prefs_first_read_context), the first `Preferences` read warms a per-UI cache from the browser's `localStorage` and must run where a UI is current — inside `mainUI()`'s `invokeLater` body or anything deeper down the UI-thread stack (frame ctors, listener callbacks). Reads from `static` initializers, `static final` fields, or `main()` before `VaadinBoot.run()` throw `IllegalStateException` at first access — the exact same safe-call-site rule as `BrowserTimeZone.get()` above, so triaging one triages both. *Detect:* grep `Preferences\.(userRoot|userNodeForPackage|systemRoot|systemNodeForPackage)` and check whether any hit is reached from a static seam. *Fix:* defer the read into the UI-thread stack — the typical Swing shape ("restore window bounds" in the frame ctor) is already safe. Related but distinct: `systemRoot()` / `systemNodeForPackage()` are inert (writes WARN via `EHelper.onUnimplemented`, reads return empty) — a per-browser store can't represent machine-wide settings. *LLM:* **judgment (low) · secret-free** — detection is grep-complete; the fix is code motion (defer the read into a UI-thread call site), which needs a little call-flow reasoning but is bounded, and the throw makes a miss loud.

- <a id="H_background_thread_context"></a>**The app's own background threads carry no `EmulatorContext`.** A `VaadinSession` lives on the UI thread, so work the app starts itself — a raw `Thread`, an `ExecutorService`, a scheduler — cannot see whose user it serves unless the context is carried to it. `SwingWorker` does this automatically; the app's own threads do not, and **two separate things go wrong on them**. *(a) Dates drift:* a `vaadinx` `SimpleDateFormat` / `Calendar` falls back to the **server** zone, with a once-per-thread WARN. *(b) Component updates throw:* per [D_no_context_throws](../../emulators/decisions.md#D_no_context_throws) a Swing→peer write from a context-less thread raises `IllegalStateException` rather than being dropped, so a background thread that touches a component fails loudly. **One fix serves both**: an app's own executor gets the context with one line where the pool is built (`EmulatorContext.wrap(executor)`, [D_emulator_context_wrap](../../emulators/decisions.md#D_emulator_context_wrap)); a hand-rolled `Thread` takes the long way — capture `vaadinx.EmulatorContext.get()` on the UI thread and wrap the work in `ctx.run(...)` / `ctx.call(...)` ([D_date_emulators](../../emulators/decisions.md#D_date_emulators)). Wrapping the pool is not sufficient on its own: the **submit** must also happen on a thread that has a context, which is why the throw names the submitting frames when it can ([D_submit_site](../../emulators/decisions.md#D_submit_site)). *Detect:* grep `new Thread` / `Executors\.` / `ExecutorService`. *Fix:* wrap the executor, or carry the context by hand; a pool that touches no component and formats no user-facing date can be left alone. *LLM:* **judgment · secret-free** — the executor case is one mechanical line at the pool's construction; a hand-rolled thread requires capturing `EmulatorContext.get()` on the UI thread and threading it into the background work. Neither failure is silent: (a) WARNs once per thread, (b) throws with the fix in the message.

- <a id="H_worker_scope_reads"></a>**Session- or tab-scoped state read from `SwingWorker.doInBackground`.** A worker carries the user's `EmulatorContext` — the zone, and the session its component updates reach the browser through — but no *current* `VaadinSession` or `UI`, so every static the sweep routes to session or tab scope is unreachable from its body: `AppInstance.get()` and a `VaadinSession.getCurrent()`-based shim both throw ([`former-singletons.md` § What still throws](../../guides/1-swing-to-emulators/former-singletons.md#what-still-throws)). On the desktop the same read was an ordinary static access, so nothing about the body looks wrong until the routing lands. Component writes from the body are a different matter: they are off the UI thread but tolerated — each hops onto the session's UI synchronously ([D_attach_aware_hop](../../emulators/decisions.md#D_attach_aware_hop)) and the first one WARNs once — and they stay as they are. *Detect:* grep `doInBackground`, then check each body, and everything it calls, against the sweep's session and tab verdicts. *Fix:* read the value on the UI thread before `execute()` and pass it into the worker. *LLM:* **judgment · secret-free** — the grep lists the bodies, but whether one reaches a routed field goes through its call graph. Not silent: the read throws.

- <a id="H_shared_calendar"></a>**Shared mutable `Calendar`.** A `Calendar` stashed in a `static` / shared field and mutated from more than one thread is unsound on a multi-user server — it was already racy on the desktop, only masked by single-threaded EDT use; the zone emulator does **not** make it thread-safe. *Detect:* grep `static .*Calendar`. *Fix:* unshare it — construct one per use (`Calendar.getInstance()` / `new GregorianCalendar(...)` inside the method that needs it). *LLM:* **judgment (low) · secret-free** — the fix is mechanical (construct per use); recognizing the shared-mutable race is the judgment, and it's a latent correctness bug (no compile/WARN signal), so lean on the grep.

- <a id="H_unswapped_printing"></a>**Unswapped printing code prints on the *server*.** `java.awt.print` and `javax.print` are not `javax.swing`, so a missed `PrinterJob.getPrinterJob().print()` *compiles cleanly* after the import-swap and then either throws `PrinterException` (headless server, no print service) or — worse — silently spools to the **server's** print queue; `job.printDialog()` throws `HeadlessException`. This is the only known gap that bypasses the `EHelper.onUnimplemented` WARN funnel — no `vaadinx` class sits in the path to WARN from — so detection is purely a source scan. *Detect:* grep `java\.awt\.print` and `javax\.print` imports, plus `\.print\(\)` calls on tables/text components. *Fix:* hand-crafted `Printable`s → add `:emulators-printing` + swap the `PrinterJob` import ([D_printing](../../emulators/decisions.md#D_printing)); component-print sites (`JTable.print()`, `JTextComponent.print()`, `printAll`) and `javax.print` service code → rewrite to a server-side PDF report (JasperReports, openhtmltopdf, or a hand-crafted `Printable` against the virtual printer). *LLM:* **mechanical / likely-human · secret-free · ⚠silent** — the `PrinterJob` import swap is mechanical; the component-print → PDF-report rewrite is likely-human (a redesign). ⚠silent because this is the one gap that bypasses the WARN funnel (no `vaadinx` class in the path) — detection is *purely* the source scan, so the grep is load-bearing here, not a convenience.

- <a id="H_platform_shellout"></a>**Shell-outs and platform checks — the machine they describe is now the server.** `Runtime.exec`, `ProcessBuilder` and `java.awt.Desktop` compile and run, but on the server. A command whose job is to show something to a human (`cmd.exe /c start`, `xdg-open`, `open`, `Desktop.browse` / `open` / `print`) either opens it where no user is looking, or fails on a server OS it was never written for. Platform checks (`SystemUtils.IS_OS_*`, `os.name`, `System.loadLibrary`) evaluate fine and describe the server; what matters is what they gate. *Detect:* grep `Runtime\.getRuntime\(\)\.exec|ProcessBuilder|Desktop\.getDesktop` for the calls and `IS_OS_|os\.name|System\.loadLibrary` for the checks. *Fix:* classify by intent, per [M1D_platform_checks_shellouts](./decisions.md#M1D_platform_checks_shellouts). Backend intent stays; check the working directory, and that the binary exists on the server. UI intent moves to the browser: a download, `Page.open` / `Anchor`, the virtual PDF printer, or `mailto:`. Hardware at the user's end genuinely breaks. *LLM:* **judgment · secret-free · ⚠silent** — the grep finds every site, and the intent call is a local read of what the command opens. But a UI shell-out left in place compiles, boots, and only fails when the menu item is clicked, on the server, where nobody sees it.

- <a id="H_htmldocument_mutators"></a>**HTML-pane code that *mutates* through `HTMLDocument`.** Reading the element model works: a `text/html` pane's `getDocument()` is a real `HTMLDocument` ([D_htmldocument](../../emulators/decisions.md#D_htmldocument)), so `((HTMLDocument) pane.getDocument()).getElement(id)`, `getDefaultRootElement()` and `getCharacterElement(off)` all resolve, and `setBase` round-trips (redirecting nothing — links resolve against the loaded page). **Writing does not:** `insertBeforeEnd`, `setOuterHTML`, `setInnerHTML`, `insertAfterEnd` and friends WARN and change nothing, because the model is a read-only projection of the pane's markup. Two smaller traps behind the same API: `getElement(id)` sees only **server-authored** markup (the editor drops `id` on the way back from a browser edit), and `getIterator(HTML.Tag)` answers `null` for **block** tags — the JDK's own contract, not a gap. *Detect:* grep `insertBeforeEnd|insertAfterEnd|insertBeforeStart|insertAfterStart|setOuterHTML|setInnerHTML`. *Fix:* append-shaped mutation — a transcript or console pane, and 7 of the 9 mutating files in the surveyed corpus — → read-concatenate-set: `pane.setText(pane.getText() + html)`. Interior-element splicing → rebuild the document string and `setText` it. *LLM:* **mechanical / judgment · secret-free** — the append rewrite is mechanical and grep-complete; interior splicing is judgment, since there is no write path to port onto (tracked as the write half in [#14](https://github.com/vaadin/swingbridge-emulators/issues/14)).

- <a id="H_html_pane_links"></a>**Relative links in an HTML pane silently stop being links.** Flow sanitizes what reaches the browser with a protocol allowlist for `a[href]` (`http`, `https`, `mailto`, `ftp`), so a relative href (`topics.html`), a root-relative one (`/help/x.html`), a `file:` / `jar:` URL, or a bare `#fragment` **loses the attribute entirely**. An hrefless anchor is no longer a link: it renders as plain text, can never be clicked, and no `HyperlinkListener` fires. A help set whose pages link to each other relatively — the usual way to write one — therefore arrives with its navigation gone, with no exception, no WARN, and nothing in the log. Absolutizing hrefs at load time does *not* rescue it: the resulting `file:` / `jar:` URL is stripped by the same allowlist ([SD_hyperlink_listener](../../surrogates/decisions.md#SD_hyperlink_listener)). *Detect:* grep `addHyperlinkListener|\.setPage\(` to find the panes, then inspect **the app's HTML resources** for `href="` values that aren't `http` / `https` / `mailto` — the evidence is in the markup, not the Java. *Fix:* link by `http(s)` URL (a made-up host is fine, nothing is fetched) and map those URLs onto your own resources inside the listener — which is where Swing already puts the decision. *LLM:* **judgment · secret-free · ⚠silent** — the listener rewrite is small, but detection reaches outside the Java source into resource files, so the grep narrows the search rather than completing it. ⚠silent because a dead help viewer produces no runtime signal at all.

- <a id="H_multi_tab"></a>**Multi-tab.** Each tab is a fresh UI, but one JVM serves them all: in-process state (Java collections in static fields, file handles cached at startup) is shared across every tab and every user — per-JVM, not per-app-instance, which is the inversion of the desktop assumption. Apps that assume singleton instance-per-process behaviour will see surprising state divergence. *Detect:* identify singletons that hold mutable user-visible state. *Fix:* move to session-scoped storage or shared `VaadinSession` attributes. Our own side of the invariant (one app per session, a second tab curtained) is open beyond alpha — see [#25](https://github.com/vaadin/swingbridge-emulators/issues/25). *LLM:* **judgment · sensitive · ⚠silent** — this *is* the static sweep from the user-scoping angle (`Q_user_specific` → session): the state is the app's own user data, so it's on-prem only, and a mis-scope is silent (leaks cross-user under load). The hard corner (sensitive ∧ silent) → **human review-gate** on the finite per-field verdict table. This is the `Q_user_specific` branch of the static-state scope model above — tree + examples in [`static-fields.md`](../../guides/1-swing-to-emulators/static-fields.md), rationale in [M1D_static_taxonomy](./decisions.md#M1D_static_taxonomy).

- <a id="H_uncaught_handler"></a>**`Thread.setDefaultUncaughtExceptionHandler` and `Thread.UncaughtExceptionHandler`.** A JVM-wide handler is *the* supported way to see an EDT throw (the `sun.awt.exception.handler` alternative was removed in JDK 7), so in a Swing app it is usually the app's error dialog — but it can equally have been installed to make a dying library thread visible (a CORBA/JMS reader, a `java.util.Timer`). Under SB-Emulators the EDT's throws reach the session `ErrorHandler` instead, and the JVM-wide hook is never consulted ([D_uncaught_handler_chain](../../emulators/decisions.md#D_uncaught_handler_chain)). *Detect:* grep `setDefaultUncaughtExceptionHandler\|Thread.UncaughtExceptionHandler`. *Fix:* **split the handler by what its body does, not by why it was installed.** (1) Move everything that touches Swing or the UI into the session `ErrorHandler` — the `AppErrorHandler` Phase 4 installs from a service-init listener ([M1D_error_handler_default](./decisions.md#M1D_error_handler_default)); it runs there with a current UI, so a ported handler can still open a dialog — through `SwingUtilities.invokeLater`, since the handler does not always run on a thread that can park (an exception from outside `callSwing` reaches it on the request thread, where `EventQueue.isDispatchThread()` still answers `true` and a direct modal call throws). (2) Whatever is left decides the registration: nothing → delete the `setDefaultUncaughtExceptionHandler` call; a UI-free remainder (logging, metrics, an error reporter) → keep it registered, since nothing else in the migrated app covers a dying `new Thread()` or library thread. **If you keep it, guard its body with `if (UI.getCurrent() != null)` around anything UI-touching** — the same guard the Phase 4 `AppServlet` listing uses: a kept handler is now invoked in two worlds, and from a dying pool thread there is no UI, no session and no lock, so a UI-touching body throws from inside the error handler. Three other things a kept handler must not do are gated elsewhere: calling `System.exit` (the guardrails' JVM-exit gate), holding mutable state (the Phase 1 static sweep), and clobbering a shared container's own default (only an issue if you deploy as a WAR next to other apps — with Vaadin Boot your `main()` owns the JVM). *LLM:* **judgment · secret-free** — grep-complete, and the split is mechanical once the body is read, but which half is "UI-touching" is a reading of the app's own code.

- <a id="H_edt_thread_handler"></a>**A per-EDT `Thread.currentThread().setUncaughtExceptionHandler(h)`.** The rarer per-thread variant: set from inside the EDT, so it catches EDT throws without going JVM-wide. It has no counterpart here and **silently does nothing** — there is no stable EDT thread to hang it on (the UI thread differs per request, and the virtual thread a callback runs on dies immediately), and `java.lang.Thread` is not SB-Emulators' to hook. *Detect:* grep `currentThread()\.setUncaughtExceptionHandler`. *Fix:* same as [`H_uncaught_handler`](#H_uncaught_handler) step 1 — the handler body moves into `VaadinSession.setErrorHandler(...)`; there is no step 2, since a per-EDT registration covers nothing else. *LLM:* **mechanical · secret-free · ⚠silent** — grep-complete and a fixed transformation. ⚠silent because the call compiles, runs and has no effect whatsoever.

- <a id="H_sun_awt_exception_handler"></a>**The `sun.awt.exception.handler` system property.** The JDK 6-era hook: name a class with a public no-arg constructor and a `public void handle(Throwable)`, and `EventDispatchThread` would call it reflectively. **It was removed from the JDK, not deprecated** — nothing in JDK 25's `src.zip` mentions it — so an app that sets this property has been silently getting the default behaviour for years, *on the desktop too*. *Detect:* grep `sun\.awt\.exception\.handler`. *Fix:* delete the property and the handler class it names, then port whatever that class did the way [`H_uncaught_handler`](#H_uncaught_handler) describes. Emulating the JDK 6 behaviour would mean inventing a mechanism the migrator's own JDK no longer has. *LLM:* **mechanical · secret-free** — grep-complete; the deletion is unconditional, and porting the named class's body is the same split as above.

- <a id="H_layout_numbers"></a>**Reading layout numbers** (`getPreferredSize()`, `getBounds()`, `getWidth()`, `getHeight()`). Per M1D_layout_close_enough, these return dummy values, not rendered geometry. *Detect:* grep for these methods used in conditionals or arithmetic. *Fix:* rewrite layout-dependent logic to Vaadin equivalents (CSS-based positioning, Vaadin layout components). *LLM:* **likely-human · secret-free** — grep surfaces the sites, but rewriting logic that branches on pixel geometry is open-ended and app-specific; the dummy values (M1D_layout_close_enough) make the divergence quiet, so expect to hand off.

- <a id="H_plaintext_http"></a>**Every component value now crosses the network — passwords included.** On the desktop a value shown in a component never left the process. In the browser, every value a component shows travels to the user's browser and sits in its page, and every keystroke travels back the same way: a `JPasswordField`'s text is in the page as the field's value, and a field the app pre-fills from storage sends that stored password to the browser. Over plain HTTP all of it is readable by anyone on the network path. The migrated app itself cannot fix this, since Vaadin has to send the value to render the field. *Detect:* grep `JPasswordField` — the sharpest signal, though the hazard covers every component. *Fix:* serve the app over HTTPS in production, with TLS terminated at the app or at a reverse proxy in front of it. *LLM:* **mechanical · secret-free** — grep-complete, and the fix is deployment configuration rather than code; the agent's job is to tell whoever deploys the app, not to change the app.

- <a id="H_cancelable_close"></a>**Cancelable tab close** (`WindowListener.windowClosing → event.consume()`). The browser owns the unload prompt; the app can't override the user's choice. `event.consume()` is a no-op for tab close. *Detect:* grep `windowClosing` and `event.consume()`. *Fix:* the main window's `WINDOW_CLOSING` still fires after the tab is gone ([D_shutdown_lifecycle](../../emulators/decisions.md#D_shutdown_lifecycle)), for cleanup only. `consume()` / `DO_NOTHING_ON_CLOSE` cannot keep the tab open, and a modal dialog inside the listener throws `IllegalStateException`. Keep the dialog-free cleanup and turn confirm-on-close into saving on change. Whether to add a `beforeunload` prompt is still open ([#9](https://github.com/vaadin/swingbridge-emulators/issues/9)). *LLM:* **judgment · secret-free** — grep-complete; the fix (redesign confirm-on-close into proactive save) is a bounded pattern, but the design is still open upstream, so treat as escalate-if-unsure.

## 8. Worked example

[`testapps/crud`](../../testapps/crud) is the canonical step-1 worked example. Three subdirectories, one per migration-arc stage:

- `swing/` — stage-1 input shape: a small employee-CRUD app on stock Swing.
- [`1-emulators/`](../../testapps/crud/1-emulators) — stage-2 output. **Landed.** The diff between `swing/` and `1-emulators/` *is* the canonical "what changes during step 1" reference; stumbles encountered during the migration are logged in [`1-emulators/STUMBLES.md`](../../testapps/crud/1-emulators/STUMBLES.md). Run via `./mvnw -C clean install -DskipTests && ./mvnw -C -pl testapps/crud/1-emulators exec:exec`.
- `surrogated/` — stage-3 output (not landed yet). Out of scope for this spec.

The app exercises a typical CRUD component baseline: `JTable` list view, `JTextField` / `JCheckBox` / `JComboBox` / `JSpinner` detail form, `JOptionPane` confirms, `JDialog` edit-form host, `JMenuBar`. It also leans on a handful of stock-Swing classes outside the originally-supported surface (`BoxLayout`, `GridBagLayout`, `JScrollPane`) on purpose — those surfaced as compile-time blockers during the walkthrough, alongside `JSpinner.DateEditor`, `ButtonGroup` cross-package coordination, and `JFormattedTextField`. All landed; the current `1-emulators` app boots with four triaged WARNs — two cosmetic `Window.setLocationRelativeTo` (R_match_swing_errors sub-bucket (b)), two `SJSlider.setPaintTicks` / `setPaintLabels` (R_match_swing_errors sub-bucket (a) blocked-upstream).

The diff between `swing/` and `1-emulators/` is the most useful reference for what step 1 looks like end-to-end; this spec + the recipe in §3 frame *why* each change is needed.
